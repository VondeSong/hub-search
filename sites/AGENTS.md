## 每次修改

1. 读取所在分支当前状态、该站 `.source-snapshot.json` 和 Sites 最新源码/发布状态。先核对来源，再决定从哪一端继续，不能把旧镜像覆盖到新版本上。遇到双方改动要审查并合并，禁止强推或无差别替换。导入期间独占对应站点目录，暂停其他编辑任务；导入锁不约束普通编辑器。
2. 保留项目运行方式、`.openai/hosting.json`、锁文件、静态资源、现有示例数据和用户可见功能。手机端与任务流程实验室的 `dist/` 全部属于源码；工作台的框架 `dist/`、`node_modules/` 等是产物/依赖，不能纳入镜像。
3. 只运行与修改有关的必要检查。源码原样导入要比对文件清单与字节哈希；功能修改需执行相应现有检查，必要时再做浏览器验收。未执行的构建、浏览器或真机验收不得写成通过。
4. 修复交付包含两个独立结果：原 Site 的更新和 GitHub 源码的远程同步。在 Sites 发布成功后，以实际发布的源码提交更新镜像与 `.source-snapshot.json`；同一任务创建一次中文 GitHub 提交并核验远端。用户明确要求只保存源码或暂不发布时服从当次限制，并写明线上仍是哪一版。
5. GitHub 中存在本次编辑时，先把这些修改应用并核验到对应 Site 源码，不能用导入命令覆盖自己或其他人的尚未合并修改。导入工具拒绝镜像已变化时应审查差异，不得删除快照或放宽校验来绕过保护。
6. `.source-snapshot.json` 是上一次从 Sites 原始 Git 提交导入的清单。编辑期间 `verify` 报告差异是待同步状态；不能手改哈希伪造已经同步。完成时应按实际发布来源重建记录。源代码不会携带浏览器 localStorage / IndexedDB 数据、运行数据库或账户凭据。
7. 任何一端受阻都明确报告具体状态与已保存提交。维护步骤不等于已配置后台自动监听；不要声称 GitHub push 会自动部署 Sites，也不要声称普通站点操作会自动产生 GitHub 提交。

## Claude 与 Codex

Claude Code 可在本仓库对应目录编辑；接管时读取本文件与根规则。若当前工具不能发布 Sites，将可验证的源码提交保存在 GitHub 并说明尚待发布，再由有 Sites 能力的会话沿用同一项目部署。不得另建网站并把新网址当成原站更新。
