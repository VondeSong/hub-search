# Hub 内模型衔接与记忆管理验收（#21）

范围来自 [Issue #21](https://github.com/VondeSong/hub-search/issues/21) 顶部当前的九项场景，平台为本机 Windows。历史调研中的外部软件共享、OpenViking、Notion 接入继续后置；本轮沿用 SQLite、Basic Memory 和现有任务/成果真源。

## 本轮实现

- 长回答超过初始历史预算时保留带消息身份的片段，近期用户要求继续进入上下文。新增 `conversationHistory`，支持当前事项分页、精确消息及 Unicode 字符范围补读，每次最多 6000 字符；沿用当前授权、来源及成果依赖核验。目标、最新修订、任务、working state、业务回执分别由既有正式入口提供，历史回答不作为操作完成凭证。
- 模型通过 `proposeMemory` 提交待确认建议。项目由事项当前已启用范围决定；来源必须显式选择当前事项的真实用户消息。建议不参与召回，用户可在共享记忆面板检查、修改、确认或忽略。重复请求保持幂等，过期版本及跨项目确认拒绝；每个项目最多保留 50 条待确认建议。
- 用户确认生成不可变修订，记录来源事项、消息、运行、提议提供方、用户确认时间和修改原因；面板显示更新时间、来源和修订记录。旧记忆中未保存的元数据明确标为旧记录，不补造确认历史。
- Basic Memory 检索先用有效修订 permalink 限定候选，再做向量选择；Hub 仍独立核对项目、状态、版本、正文哈希和预算。使用记录区分实际提供的版本、未被检索选中及受容量限制的条目，不把“提供给模型”当作已经采纳。
- 修订、停用、遗忘及范围变化继续使运行绑定失效。依赖已失效记忆的旧回答不再进入模型上下文或历史补读；历史记录在数据库中保留，界面解释隐藏原因。旧上下文不能发布结果，需要停止或继续新一轮。
- 直连模型的完成核对错误接入原有的一次纠错额度。宿主不改写虚构要求编号，也不放宽目标、真实成果凭证、取消、来源或记忆有效性门禁；纠正失败仍拒绝交付。
- DeepSeek 完成对象的兼容仅处理已确认严格合同根层的 null / 空字符串占位，以及与实际条目数一致的冗余计数；目标绑定、要求条目、证明引用和非空未知字段保持原值。必需报告字段缺失继续拒绝，不代填结果、问题或限制说明。
- 桌面补验发现已有 schema 83 数据库跳过了新增记忆表的迁移，面板报 `no such table: memory_sources`。将数据库版本提升至 84，让正式启动补齐建议和来源表；旧条目保留并明确标为旧确认记录，不补造来源。

## 使用方式

在事项的共享记忆中选择项目并启用相应范围。让模型提出需要长期保留的规则或决定后，打开“待确认建议”，检查并修改，再点“确认并保存记忆”。修改已有条目会形成新版本；停用及遗忘会撤回未来记忆供给。面板支持刷新，重新展开也会回读当前状态。

新聊天会自动沿用最近一次主动选择的记忆范围和开关，正常重新打开 Hub 后仍保留；Codex 和 DeepSeek 共用这一默认值。首次使用保持关闭，已有聊天沿用自己的设置，浏览旧聊天不改写默认值。沿用开关不会自动保存聊天内容或确认模型建议。

遗忘无法抹去已经发送给模型的文本或已有备份。Hub 撤回的是后续使用资格，并使受影响的原生会话绑定失效；用户原始聊天指令、真实操作回执和其他仍有效的成果继续保留。
