# 换模型时，原来的真实工作能不能继续

关联：[#21](https://github.com/VondeSong/hub-search/issues/21)。本次只处理材料额度拦截，并重新检查来回换模型。

## 用的是哪项工作

沿用 Hub 已有的“工程资料整理”工作，以及它原来选择的三份资料：Car《线束数据管理》、OS《优化当前 Obsidian 库的文件夹结构》和已有 Craft 层级讨论。不另建示例资料，不改原笔记和工程文件。

之前换到 DeepSeek 时，Hub 在模型回答前就提示“单次请求材料超过本轮预算上限”。因此，之前那次不能算 DeepSeek 接手成功，也不能算 Codex 接住了它的答复。

## 本次怎么改

同一套资料库规则，在总说明和资料读取记录里重复出现。本次让模型在一份请求里读到一次完整规则，其余重复位置指向这份内容。不同范围、不同版本的规则分别保留；最新聊天、来源原文和操作结果仍然提供。

材料额度和原来选的三份资料保持原值。确实超过额度时仍然拦截。

第一次更新后，Codex 能接着回答，但 DeepSeek 仍在发送前超限。因此继续处理另一处浪费：DeepSeek 的请求还带着当前明确不能使用的工具参数说明。现在只去掉这些不能调用的参数，保留可用工具的完整说明和不可用原因，并记录每次准备发送的大小。没有删聊天或原文，也没有提高额度。

## 为什么三份资料也会超限

可以把一次请求理解成寄给模型的一包材料。里面除了原文，还有聊天、规则、工作进度、工具说明和回答格式。这些都占地方，不能只数资料有几篇。

| 限制 | 当前数值 | 是什么意思 |
| --- | --- | --- |
| 助手一次请求 | 196,608 字节，即 192 KiB | 一包最多装多少；本次是在这里被拦住 |
| 普通模式一轮累计 | 1,048,576 字节，即 1 MiB | 从按下发送到这一轮结束，多次请求合计的额度 |
| 深入模式一轮累计 | 3,145,728 字节，即 3 MiB | 深入模式的累计额度；不自动提高单包上限 |

如果这项工作另有已确认的材料计划，累计额度还可能更低。这里的字节数不是汉字数、模型 token 数，也不是账户余额。常见汉字在 UTF-8 中占 3 字节，字母通常占 1 字节，不能把 192 KiB 理解成 19 万个汉字。

这次失败记录实际采用深入模式，累计额度是 3 MiB；但在第一包的 192 KiB 检查处就被拦住，尚未消耗累计调用额度。旧失败记录没有保存被拦请求的分项大小，因此不能从“已发送 0 字节”反推它没有材料或给出精确峰值。

当前直接模型的发送前计算是：**提示文字和材料大小＋回答/工具格式大小＋256 字节预留**。这是 Hub 的请求估算，不是网络上最终发送大小或服务商账单。新记录会保留这三项，即使因为超限没有调用模型，也能查清原因。

**峰值**取一轮中最大的一包；**累计量**把各包相加。例如两次分别为 120 KiB 和 150 KiB，峰值是 150 KiB，累计是 270 KiB。这个例子仅说明算法，不是真实验收数字。

需要上限来防止不断堆积材料和重复读取。但 192 KiB 是 Hub 当前设定的保护值，不是模型能力的证明。本次先减少无效负担并实测。后续是否调整，应区分模型可接收容量、为回答留出的空间和用户愿意承担的费用，依据真实工作决定，不能只把数字调大或要求用户无理由删资料。

## 普通人可以照着做的检查

| 步骤 | 怎么操作 | 应该看到什么 |
| --- | --- | --- |
| 1. 先让 Codex 接着工作 | 从历史打开原工作，让 Codex 列出三项动手前要核对的事，说明哪些还没做。这次只讨论。 | 能根据原资料继续回答，不把计划说成已经执行。 |
| 2. 换成 DeepSeek 修改清单 | 保留原资料，换 DeepSeek，把刚才三项合成两项，并请它各起一个之前没用过的短标题。 | 能正常回答，不再被同一处重复材料拦住；回答保留最新的“两项”要求。 |
| 3. 再换回 Codex | 只问“原样列出上一条回复的两个新标题，再说明哪些工作还没做”，问题里不告诉它标题。 | 正确说出 DeepSeek 刚起的两个标题；仍说明整理尚未执行。 |

换回 Codex 后只会重新起标题，或者需要用户把标题抄给它，都不算通过。没有发生的迁移、归档或保存被说成完成，也不算通过。
