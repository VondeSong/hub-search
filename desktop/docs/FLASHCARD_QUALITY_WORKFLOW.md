# 闪卡质量反馈与 AI 改进

## 使用入口

- 复习、查看卡片、收件箱：点击“反馈”。质量反馈与重来 / 困难 / 记得 / 轻松评分独立。
- “记录并继续”保存快照；“记录并暂停此卡”保留复习历史；“记录后编辑”进入原卡编辑器。
- 勾选“将这条反馈用于以后制卡”后填写长期规则。规则可以限制为牌组、主题或学习目标，并记录例外和正反例。
- 侧栏“质量与制卡偏好”：处理反馈、编辑或停用规则、导出 Markdown 文档、进入 AI 改进。

## 第一阶段：制卡前读取偏好

`hub_get_flashcard_quality_context` 接收 learningGoal、deckId、topics、documentIds，返回 revision、scope、匹配规则与相关反馈。相关反馈最多 40 条，并返回总数与截断标记。

生成器提交 `hub_submit_flashcard_drafts` 时附 `qualityContext: {revision,scope,ruleIds,excludedTargets}`。存在生效规则时服务器要求读取版本及全部匹配规则编号；版本过期会拒绝提交。可选 `ruleApplications:[{ruleId,decision:"applied"|"exception",reason}]` 记录采用或例外理由，必须引用适用规则并填写理由；这是 AI 的处理说明，不是服务器的语义判定。规则例外不会取消单卡的“避免重复生成”标记。精确重复的已排除目标仍会被拒绝。语义层面的偏好符合性需 AI 对照原文检查，传输成功不等于语义验证通过。

导入事务从当前生效规则生成 `qualityContext.ruleSnapshots`，保存规则正文、范围、学习目标、例外和牌组名称。单卡的 generation 不能覆盖这份上下文。收件箱“制卡依据”展示提交时规则、AI 处理说明和本批次排除目标；旧草稿缺少正文快照时，仅按需读取当前规则并标注“提交时正文未记录”，不补造历史证据。

反馈和规则本地修改时保留旧版本；同步比较不同版本时保留双方内容与采用版本的记录。历史采用确定性编号，旧快照重放不会重复添加相同版本。版本选择仍按 updatedAt、相同时间的稳定排序进行，不自动逐字段合并或恢复旧内容。质量管理页“修改历史”和导出文档均展示保留版本；不同版本可能来自先后修改，不能仅据此宣称发生并发冲突。升级前已被覆盖且没有历史的内容无法追溯。

同步保留的快照中可能包含当前采用版本。导出文档按完整版本编号排除当前快照，避免把当前内容重复列为“旧版本”；存储及同步记录仍保留该快照以供核对。

已排除目标的来源匹配与导入解析使用相同的 sourceDocumentId / source_document_id 等字段，支持顶层或 source 内嵌结构。双方均有文档编号时以资料库及文档编号为准；本地 PDF 无编号时用完整来源路径及原问题匹配。Windows 路径忽略大小写、统一正反斜杠及重复分隔符，其他目录中的同名文件不会命中；URL 和 Unix 路径保持大小写。此检查识别精确原问题，不代替语义去重。

反馈保留创建时的卡片快照，之后编辑或删除卡片不会抹去反馈。反馈、规则、规则历史和 AI 请求/建议随闪卡快照同步。Markdown 文档由当前记录生成，不自动改写 Craft / Obsidian 源笔记。

Android 导出在打开系统保存页前，将当前文档快照原子暂存到应用私有目录。独立原生页面通过 Activity Result API 接收保存结果并写入目标文档；保存期间 Hub 被系统回收时，恢复的页面仍可读取暂存内容。前端提示“请在系统对话框中完成保存”，只有原生写入成功后才提示导出完成；成功或取消后清理本次私有暂存文件，不删除用户选择的文档。恢复机制参考 [Android Activity Result 生命周期说明](https://developer.android.com/training/basics/intents/result)。

## 第二阶段：AI 建议闭环

1. 在“AI 改进”选择牌组与目标，创建“反馈整理”或“现有卡片检查”请求。
2. 将界面给出的请求文字发给已连接 Hub MCP 的 AI。Hub 本身不会启动模型或后台代理。
3. AI 调用 `hub_get_flashcard_quality_work`，读取全部 nextOffset 分页，核对原文及现有规则。
4. AI 调用 `hub_submit_flashcard_quality_proposals` 保存规则或改写建议。每批最多 100 条，最终 complete=true 并给出覆盖范围和未能核对的部分。
5. Hub 每 5 秒刷新建议列表。用户查看规则范围、依据、例外或卡片前后对比，然后逐条接受或忽略。
6. 改写默认保存为新卡并保留原卡；也可替换原卡内容并保留复习计划。内容或规则版本变化后，旧建议需重新生成。

### 提交建议结构

规则建议：`type:rule`、reason、feedbackIds、rule。rule 包括 title、text、scopeType（global/deck/topic）、scopeValue、learningGoal、exceptions、positiveExample、negativeExample、enabled。

改写建议：`type:rewrite`、reason、cardId、fingerprint、evidence、after。after 包括 question、answer、explanation、cardType、cardData。原媒体与来源位置保留，接受改写时更新已核对的来源版本和证据；新增图片遮挡需使用完整卡片编辑器。

MCP 不提供接受建议的接口。提出建议不修改生效规则、原卡或评分。改写指纹不包含复习次数，因此普通复习不会使建议失效；编辑卡片内容会使其失效。

## 统计与范围预览

反馈变化比较最近 30 天和之前 30 天的分类数量，以创建时间计数。它是反馈数量，不是质量评分或错误率，需结合复习量理解。

规则的“查看影响范围”展示范围内卡片总数与前 30 张预览。命中范围不等于违反规则；AI 检查还需学习目标与来源证据。

## 验证关注点

数据库升级 / 重开、无效规则事务回滚、暂停不改变评分与计划、同步旧版本不重新启用停用规则、待确认建议不修改原卡、逐条接受同批规则、旧改写拦截、改写保存新卡 / 保留计划、UI 错误反馈。

- 回归覆盖手机反馈 → 序列化同步快照 → Windows 读取和处理 → 手机接收处理状态，以及旧快照重放不回退新状态。

## 后续修复（源码，尚未重新发布）

- Android 质量文档导出通过系统返回的 content URI 写入，使用文档提供器授予的权限，不将 URI 当作本地文件路径。
- MCP 提交与事务内导入校验均按实际 deckName 查找牌组，并结合卡片 tags 检查适用规则；声明的 deckId 与目标不符时拒绝。
- 同一批次中的卡片不得用 deckName/deck_name 改投其他牌组；应按牌组分别读取质量上下文并提交。目标名称存在重复时要求先消除歧义。
- 验证覆盖漏传牌组、漏传标签规则、错误牌组上下文和单卡改投牌组。安卓原生桥接编译通过；系统保存对话框的实机导出尚待验证。

### 同步体验后续优化（源码，尚未重新发布）

- 闪卡自动同步使用独立后台循环，每 5 秒检查持久待同步状态，不再被资料库索引、资源维护或资料库同步阻塞；保留失败重试间隔。MCP 写入的建议通过同一持久状态被发现，Hub 必须处于运行状态。
- 质量管理页处于前台时每 30 秒检查同步；重新回到前台也会检查。应用后台挂起或退出时不承诺即时同步。
- 质量同步入口合并并发请求，最近 30 秒成功且没有本地更改时复用结果；同步期间的新更改由持久待同步标记保留，后续后台任务继续处理。
- 界面显示正在同步、本机保存、待同步、失败、已同步至云端，以及上次成功时间；提供立即同步按钮，不宣称其他设备已收到。
- AI 规则建议的确认卡展示学习目标限制，空值明确显示不限制学习目标。

本轮验证：10 项质量后端测试通过；npm run build 中 TypeScript 类型检查通过并进入 Vite 转换。组件测试在 forks 和项目 test:ci threads 模式下均因 worker 启动超时而未执行断言，不能记为通过。资源构建长时间未完成，主动停止；未生成新安装包，未执行实机云端往返验收。
