# 洞察直接发现与后续核对

对应 [#52](https://github.com/VondeSong/hub-search/issues/52)，承接工作台 v92 原型。这里记录桌面接入这一阶段；不把它作为整项规划、自动召回或长期观察的完成证明。

## 使用路径

1. 洞察 → 发现 → **开始发现**。选择本机已同步的笔记，可以先读原文；问题可留空。
2. 点击开始后，复用当前助手模型、原文取证、范围与累计预算，在当前窗口直接显示结果。
3. 查看引用、共同背景与适用条件，确认后**保留这条发现**。没有合格结果时可以不保留。
4. 点击**加入后续记录**，选择实际新材料并核对。界面保留原判断，显示本次结果。
5. 明确选择**维持判断并留记录**或**采用这次修订**。保存沿用原发现身份、处理状态和历史。
6. **查看历史与纠正**进入已有详情，可查看修订、补充纠正或撤回纠正。旧入口保留在“从已有分析导入”。

查看资料、打开已有结果、保存、刷新和筛选均不启动模型。后续分析需要明确点击；本阶段不启用后台观察。

## 范围与一致性

- 新建分析仅接受明确本地笔记，连同原事项已有资料最多32份；不授予整个库或目录。一次预览不会创建事项。
- 准备请求使用操作身份和完整请求指纹恢复；结果未知时先核对原请求，不能悄悄换问题再创建。
- 结果绑定本次正式用户消息之后的固定交付；原事项收到其他问题或授权版本变化后，不把其他答复当成本次结果。
- 引文读取核对当前授权、库访问状态和来源版本；读取期间访问状态变化时不返回旧内容。
- 实际使用的资料库工作约定与分析方法单独保存版本，不算事实依据；版本变化后进入待复核。回到窗口或同步资料时重新核对目标，不把此前的初次分析当成后续核对结果。
- 维持保留旧正文及其有效依赖，将本次比较和新依据保存在修订中。新旧依据任一变化仍会触发待复核。累计背景超过32段或含回顾派生依据时要求采用完整修订。
- 修订使用本次明确选择的候选，沿用既有固定交付、依赖确认、乐观版本、操作重放和历史规则；不修改源笔记。

### 公平对照怎样做

1. 冻结三种情景：旧经验用于当前工作、新材料只影响旧判断的一部分、生活／阅读经历的回顾。使用正常 Hub 本地资料和当前模型，不复制成另一套“个人资料库”。无答案、失败和错误关联也保留。
2. 两条路径拥有相同原文、检索范围、模型、分析方法和预算。Skill 路径可正常搜索、继续上下文、给结构化结果和保存，不能故意削弱基线。先固定问题与材料，再运行；重复运行只用于明确故障修复，保留首次失败与原因。
3. 分别记录首次配置成本、开始分析后的操作数、寻找材料／搬运结果／重建背景的次数、等待时间与实际模型用量。未知用量记未知。已有真实分析不能事后拼出未经测量的基线时间。
4. 正确性由原文与反例核对；“是否帮到当前事情”由用户或未参与生成的评审评价。先累计至少10条被评价的真实候选；未评价单列，不能用引用匹配、点击、保存数量或本聊天的自评分代替。6／10是小样本试点目标，不是普遍有效证明。
5. 在效果记录中分开回答：**答案是否更好、材料是否找得更全、操作是否更少、后续是否更容易接续**。如果只减少搬运，就如实定位为便捷入口与结果收藏；找回旧资料与持续更新未证明之前，不宣称独立产品特色成立。
