# Telegram 机器人收集

Telegram 内容与 X 书签、X 喜欢共用“收藏与待读”的数据库和视图。来源入口顺序为全部、X 书签、X 喜欢、Telegram；全部来源可一起搜索、筛选及按多个属性排序。

## 连接与使用

1. 在 Telegram 的 BotFather 创建专用收集机器人，取得 Token。
2. 在 Hub 的“收藏与待读 → 同步与连接 → 连接管理”选择“连接 Telegram”，填写 Token。
3. 保存后点击“打开机器人确认”，在 Telegram 发送开始消息。Hub 接收确认后绑定发送者；确认消息不会生成收藏。
4. 此后将文字、链接、图片、视频、音频、语音或文件发送／转发给这个机器人。Hub 运行时按现有同步间隔收取新消息，也支持“立即同步 → Telegram”。X 喜欢、X 书签和 Telegram 各有独立的手动同步入口。

Token 仅通过后台保存到系统凭据库，不进入数据库、页面正文、媒体地址或日志。Hub 不会删除已有 webhook；正在被其它服务使用的机器人应由原接收服务安排转存，或另外创建专用机器人。连接检查使用官方 getMe 和 getWebhookInfo，不会清空待收消息。

## 页面与附件

- Telegram 与 X 共用现有 collection_x_items 表（沿用历史表名），不建立另一个用户可见数据库。Telegram 使用独立来源值和带机器人、聊天、消息身份的键。
- 只接收已绑定用户的私聊消息；转发消息在 Telegram 提供信息时保留原始作者和来源链接。
- 相册按 media_group_id 合并为一张卡片，按消息顺序排列正文和附件。后到达的相册成员更新同一页面；重复收件不生成重复卡片。
- 编辑消息更新原页面，保留创建日期、阅读状态和用户标签。
- 与现有收藏共用待读、进行中、已读、放弃以及标签。Telegram 的状态修改只管理本地内容，不进入 X 的取消收藏／喜欢队列。
- 本地媒体通过现有受控媒体协议预览。视频优先使用 Telegram 缩略图；下载失败或超出大小限制时，正文与可下载的缩略图仍然保留。
- Obsidian 正文放在 `Telegram/收集/`，文件名与 Hub 标题一致；附件放在 `99_Meta/assets/Telegram_assets/`。沿用页面内容哈希保护，不覆盖用户已手动修改的页面。

## 接收、重试与边界

收件位置和本批消息在同一个 SQLite 事务内提交，再处理附件和 Obsidian 归档。事务失败不会推进 offset；重启后可重放。机器人收件与 X 抓取分开调度，本地归档使用现有互斥边界。归档期间新增的 Telegram 批次保留后续补写标记。

默认沿用现有 30 分钟同步间隔，0 表示只手动收件。账号确认期间每 15 秒检查确认消息。暂停会保留已收内容与待补写状态；429 遵守冷却时间，凭据失效或接收冲突暂停自动请求并提示处理。

新消息默认使用官方云端 Bot API：

- 尚未接收的消息更新最多保留 24 小时。长时间退出 Hub 可能漏收，机器人私聊历史无法通过该接收接口任意补齐。
- 云端 getFile 下载上限为 20 MB。大附件保留正文并标记待重试，不能据此承诺大文件已完整归档。
- 历史补取与大附件使用可选的 tdl 个人账号连接；不包含本地 Bot API 服务或常驻云接收服务。
- 发往机器人但 Telegram 未提供的来源、编辑或附件信息，Hub 不会自行补造。

参考：[官方 Bot API](https://core.telegram.org/bots/api)、[getUpdates](https://core.telegram.org/bots/api#getupdates)、[getFile](https://core.telegram.org/bots/api#getfile)。

## tdl 历史与大附件（0.16.215）

在“同步与连接 → Telegram 历史与大附件”点击“安装 tdl”。Hub 下载独立的官方 Windows x64 v0.20.4，先校验发布包 SHA-256，再仅解包程序及许可证。运行文件另外记录校验值，发生变化时拒绝运行并要求重装。tdl 是 AGPL-3.0 的独立工具，未将其源代码或二进制并入 Hub 包装；官方源码和许可证入口在该设置中。

安装后选择扫码或验证码登录，点击“登录 Telegram 账号”，使用**发送消息给机器人的同一个个人账号**。该连接与 Bot Token 分开。0.16.216 起扫码在 Hub 对话框中显示清晰的黑白图像；手机 Telegram 打开“设置 → 设备 → 连接桌面设备”，扫描最新二维码。二维码由 tdl 自动更新，Hub 保守地在显示 25 秒后隐藏旧图，等待下一张；也可点击“重新获取二维码”，结束原登录后建立新登录。两步验证密码在 Hub 对话框中输入，仅发给当前本机 tdl 进程，提交后清空；验证码登录仍由独立终端接收手机号、验证码和两步验证密码。0.16.217 起首次二维码或两步验证提示等待上限为 45 秒，超时显示检查网络／代理及重试建议；已取得登录提示后仍保留五分钟的扫描和确认时间。取消或关闭扫码对话框会终止当前登录并清除临时图像。

扫码使用 Windows ConPTY 保留 tdl 的真实终端交互，不另造账号协议；按固定版本半字符输出恢复方形二维码模块，保留边界，并验证二维码可解码且属于 `tg://login` 协议后才显示。验证接受上游 gotd 的带填充 URL-safe Base64 和无填充形式，拒绝无效编码及附加查询参数。登录控制台固定 UTF-8，避免 Windows 默认代码页把上半方块转换为问号。启动器先将等待中的控制台加入私有 Windows 作业，再允许它启动 tdl；取消时关闭整个作业，结束其子进程。终端刷新按屏幕光标和清除指令合并，UTF-8 分片独立解析；终端原文、二维码和密码不写入数据库、收藏事件或诊断日志。登录进程失败只返回已识别的错误类别和重试建议，不直接显示可能包含账号资料的原文。扫码确认及历史身份核对完成前，不标记账号已连接。

tdl 未单独填写代理时沿用 Hub 已有的 Windows 静态系统代理；显式填写的代理优先。不会将带有账号密码的系统代理地址传给 tdl。设置里显示实际使用的系统代理。Bot API 收件与 tdl 均可通过现有网络连接，避免 Bot API 能收件而 tdl 直接连接失败。

Hub 按绑定的账号和机器人身份检查历史，只导入该私聊中用户发送的消息；机器人回话不进入收藏。登录会话存在 Hub 本地数据目录的 `telegram-tdl/<机器人>-<用户>/session`，Windows 目录限制为当前用户访问，不复制 Telegram Desktop 的会话。

“补取历史与附件”读取当前机器人会话的全部可用历史。内容合并进现有数据库，使用同一 Obsidian `Telegram/收集/` 页面位置和 `Telegram_assets` 附件目录。机器人接口与个人账号接口的消息编号不能直接比较；稳定的历史身份、来源、发送时间、正文、附件大小和相册身份用于合并。无法唯一判断的相同消息保留各自记录，不丢弃内容。重复补取、后到相册和编辑保留原创建日期、阅读状态及标签。

默认按现有同步频率自动检查最近历史，关闭该选项后仍可手动补取。历史媒体直接交给 tdl；已收到的 Bot API 附件下载失败时，有已核对的历史媒体身份才会转交 tdl。大附件写入同一磁盘上的临时目录，检查完整文件和已知大小后才标记已下载。未完成、已删除或无法访问的附件保留原内容和待重试状态。tdl 没有云端 Bot API 的 20 MB 限制，实际受 Telegram 可访问内容、磁盘空间和网络限制影响。

tdl 使用独立的运行锁；X 同步期间可以安装、登录和补取 Telegram。最终归档仍共用现有写入锁，后台完成后继续补写。tdl 可单独暂停；已经入库的内容保留。暂停附件下载时一并暂停共享归档，避免下一附件立即重新启动下载。代理只支持带端口的 HTTP／HTTPS／SOCKS5 地址，不接受账号密码；登录或网络失败显示可重试状态，不误报完成。

参考：[tdl 官方项目](https://github.com/iyear/tdl)、[消息导出](https://docs.iyear.me/tdl/guide/tools/export-messages/)、[下载](https://docs.iyear.me/tdl/guide/download/)。

## 同步期间的本地属性

状态与标签只需短暂的本地数据库事务，同步和归档期间也可修改。页面属性写入排队处理，并按版本确认，后台旧任务不能清除较新的修改。修改进行中／完成不会触发 X 抓取；放弃仍按来源同步队列处理，发出取消请求前会再次检查用户是否撤销。已经发出的 X 请求无法保证撤回。

同步频率可在当前运行期间调整，供后续调度使用。保存位置、存储方式及附件下载开关会影响当前写入目标，因此在共享抓取／归档本轮完成后才允许修改；设置窗口说明了等待原因。

## 验证边界

协议测试使用受控 HTTP 服务，经过正式请求序列化、响应解析、事务收件和统一数据库查询；它证明 Hub 一侧的协议与存储行为。开发验证未使用真实 Telegram Token；账号绑定、Telegram 在线收件与真实附件下载需在用户连接机器人后验证，不将本地测试表述为真实账号同步成功。
