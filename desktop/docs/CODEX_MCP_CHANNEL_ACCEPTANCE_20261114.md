## 修复与保留的失败

1. **停止过早使用旧运行身份。** 真实实测中，新请求刚发出时停止按钮已经可点，但 UI 仍可能持有上一轮生命周期；后端正确拒绝旧身份，导致本轮继续执行。现改为取得实际 activeRunId 后才开放停止，并在提交前刷新生命周期；若已换成另一轮则要求核对，不能默默停止新一轮。两条回归覆盖未准入和运行身份已替换，修复后真实停止通过。没有放宽后端并发校验。
2. **旧回答保存提示误报图表。** 用户要求更新后，历史回答的保存保护正确拦截，但统一提示“图表版本已变化”，即使没有图表。改为返回已有来源核对结果中的真实原因；新增要求变化的回归，保护条件保持不变。
3. **额外验收可执行文件影响默认启动。** 添加可选验收程序后，Cargo 无法自行选择默认主程序。显式保留 `default-run = "craft-search"`；普通开发仍启动 Hub，验收程序仅在显式特性下可构建。

失败材料原样保留。夹具曾误选历史回答，随后限定到最后一条可见回答的保存按钮；`display: contents` 容器不能用自身尺寸判断可见，改为检查真实按钮。故障等待也曾误认上一轮的终止提示，已要求新的 Run 身份。锚定对话撤回单篇材料会推进事项版本，不一定提高全局授权版本；按实际范围和版本核对，没有为通过验收篡改此合同。这些夹具失败不计为产品通过，也没有追加模型来掩盖失败；保存定位修正后直接使用已完成的同一回答继续核验。

## 重现入口

夹具位于 `desktop/qa/mcp-channel-acceptance.*`，原生准备器位于 `src-tauri/src/agent_acceptance/mcp_channel.rs`。沿用现有 `integration-agent-acceptance` 特性；普通构建不注册测试 IPC、不初始化合成材料。

在 `desktop/` 构建：

```powershell
cargo build --manifest-path src-tauri/Cargo.toml --bin hub-mcp-acceptance --features integration-agent-acceptance
node node_modules/vite/bin/vite.js --config qa/mcp-channel-acceptance.vite.config.ts
```

控制器只接受已登记的独立临时数据根，并校验合成源文件、库路径及 vault 仍在根内。用 `--phase settings/run/stop/resume/narrow/unknown` 执行；原对话通过 `--work-id` 延续，设置重开使用 `--settings-work-id` 和 `--other-work-id`，保存复核可用 `--save-only` 避免再次运行模型。运行配置和每阶段结果均保留，下一次同阶段执行会先归档旧结果。

故障注入使用字节相同但名为 `hub-mcp-acceptance-failing.exe` 的副本加 `resume --failure-probe`，仅其 `--agent-mcp` 子进程故意退出；恢复改回正常程序。unknown 注入必须先有真实 verified 保存，备份该计划后才改成 unknown，绝不伪造成功回执。测试程序未指定隔离根或 MCP 参数时退出码为 2，不打开个人资料。
