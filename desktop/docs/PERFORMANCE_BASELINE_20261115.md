# 日常搜索分段观察与中文阅读检索优化

对应 [#6](https://github.com/VondeSong/hub-search/issues/6)，关联 [#13](https://github.com/VondeSong/hub-search/issues/13)。本轮只处理实际测出的阅读检索热点；不重做既有预览缓存、分页、索引调度或 #4 的功能。

## 数据、口径与环境

- 基线源码 `3433e2a`，版本 `0.16.396`；使用日常真实数据：2,776 篇文档、14,706 条内容、1,728 条阅读记录（JSON 共约 40.6 MB）、749 张闪卡，数据库 epoch 87、词法索引 schema 8。
- Windows 11 专业版 build 26200，Intel i5-12400（6 核/12 逻辑处理器），可见内存约 47.8 GiB；使用 Cargo 默认 test/debug 程序，不能将这些耗时当正式 release 包表现。
- SQLite 使用 `SQLITE_OPEN_READ_ONLY`、`query_only=ON` 和单次读取事务；不调用应用启动、迁移、抓取、同步、OCR 或写入入口。词法索引仅打开已存在的活动代际 reader，前后核对 `meta.json` 摘要。
- 本轮源库实际为 WAL 模式。复现时应先只读核对 journal mode；活动库的非 WAL 长读取事务可能阻塞其他写入，不能直接套用同一并行测量安排。
- 不创建隔离客户端资料或合成日常数据，不启动第二个 GUI。单元回归使用普通测试夹具，与日常测量分开。
- 6 个案例来自现有标题中的真实词：空查询、常见中文双字词、标题中低频中文双字词、ASCII 词、完整中文标题及单库范围；没有采用或声称拥有用户的真实输入日志。原词、来源身份和逐轮记录只在忽略目录保存。
- 每组 5 个新进程，每个进程复用 reader 连续运行 3 轮，**每案例/每段 n=15**。第 1 轮只是新进程/reader，操作系统缓存未清空；不能称为磁盘冷启动。
- 原先的 CPU <15% 空闲门槛在 45 秒内未满足，保留失败回执且没有运行样本。之后仅在无 Cargo/rustc/link 构建、连续 3 次系统 CPU <35% 时做**有常驻后台负载的日常观察**。媒体播放器、模拟器及其他任务未停止；这不是空闲基线或严格实验室控制。
- 分别测生产词法检索 50/2000 条、阅读 50 条、闪卡 50 条、模块分面 2000 条、文档 SQL 与 Craft 页面解析。词法分面只覆盖检索段，未包含标签归并等完整分面元数据聚合。
- 计时不含随后为结果核对而做的序列化/哈希。测试程序的进程资源观测包含这些核对开销，不等于产品进程资源。

## 已证热点与最小修改

原阅读查询对 JSON 中每个文字值跨 SQLite/Rust 调用并分配小写字符串。常见中文查询的阅读段中位数约 1.07 秒，完整中文标题在阅读中没有结果时仍约 1.03 秒；相同案例的词法 50 条约 9–23 ms。最大的真实 Craft Markdown 约 1.62 MB，解析中位数约 7.6 ms。本轮证据支持优先改阅读文字筛选，不支持把预览整体重写。

`module_search.rs` 对只含基本/扩展 A 区汉字的查询使用 SQLite `instr` 筛选**已解码的 JSON 文本值**，省去逐值的小写转换；其余查询沿用原有 Unicode 处理。仍在 `json_tree` 上检索，不能直接在 JSON 原始串搜索，以免漏掉 `\u` 转义的正文。可见范围、后续实际显示文字核对、标题优先、限额和实体身份都不改。

回归覆盖：转义中文、较旧的精确标题优先于较新的正文命中、仅元数据包含关键词的排除、标题范围，以及 `K`/`ẞ` 的 Unicode 小写检索。纯汉字之外的秒级阅读查询仍是已知后续热点，不能把本改动说成所有语言或整个应用的统一加速。

## 同口径结果

以下单位均为 ms，阅读段限额为 50，前后各 n=15；p95 按本组最大样本保留。

| 案例 | 原中位数 | 新中位数 | 原 p95 | 新 p95 | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| Q0 空查询 | 78.4 | 77.2 | 114.5 | 92.1 | 未走关键词筛选，无优化收益结论 |
| Q1 常见中文双字词 | 1073.7 | 419.5 | 1324.8 | 465.1 | 中位耗时降低 60.9% |
| Q2 标题中低频中文双字词 | 1377.8 | 830.9 | 1854.2 | 895.1 | 中位耗时降低 39.7% |
| Q3 ASCII 词 | 2361.7 | 2282.1 | 2595.3 | 2662.6 | 原路径，尾部升高；不宣称改善 |
| Q4 完整中文标题，阅读无匹配 | 1028.9 | 412.6 | 1335.8 | 454.6 | 中位耗时降低 59.9% |
| Q5 单库范围，阅读无匹配 | 19.6 | 19.5 | 29.4 | 24.6 | 范围筛选已先排除，不宣称改善 |

两组 10 次进程执行全部退出 0。34 个案例/段组合各 15 次结果摘要稳定，前后数量一致；阅读/闪卡的完整有序返回值、预览正文，以及词法命中的有序身份/匹配字段/正文摘要均相同。索引代际与 `meta.json` 身份一致。模块搜索定向回归 **7 通过、1 默认忽略、0 失败**，包括本轮新增回归。额外显式执行的测量入口不冒充新增的独立业务测试数量。

这些是在有背景负载下的同口径局部对照，未用资源观察反推用户窗口卡顿原因。Q3 的波动与仍存在的约 2.3 秒扫描一并保留；没有隐去不改善的案例。

被实际接受的启动前负载样本：原组系统 CPU 18.2%–33.5%（中位 22.7%），新组 18.3%–32.4%（中位 20.6%）；其他高负载门槛尝试也保留，不能说两组负载完全相同。包含 3 轮所有案例及哈希核对的单进程总时长为原组 49.95–54.28 秒、新组 38.91–39.92 秒。测试程序峰值 RSS 分别为 86.9–90.7 MiB 和 87.5–92.4 MiB，private bytes 峰值为 43.3–49.5 MiB 和 43.0–49.5 MiB；这些资源样本不支持宣称产品内存下降。

## 复现入口与证据

入口是默认忽略的 `performance_baseline::daily_readonly_baseline`，仅在显式提供 `HUB_PERF_INPUT` 时读取指定日常目录。正常产品构建不包含该测量模块，也不添加后台采样。

1. 在 `desktop/` 使用现有 `node scripts/test-rust.mjs --collect-only` 构建并核对测试 EXE/Windows manifest，从生成的回执读取 `executable`；不猜测共享 target 中哪个文件是本次程序。
2. 在数据目录以外准备私有 JSON：`root`、新的 `output` 文件名、`rounds`（1–10）、`queries`（每项含 `id/query`，可选 `field/library`）和 `previews`（`id/library/document`，可选 `page`）。只使用已存在且可见的真实资料。输出父目录须存在，程序拒绝覆盖旧回执。
3. 设置 `HUB_PERF_INPUT`，运行该回执中不可变程序：`performance_baseline::daily_readonly_baseline --exact --ignored --test-threads=1`。新的重复测量使用新输出名，先核对机器负载、活动构建、数据/代际身份。

基线程序 SHA-256：`b4fbd822614536f7e9a1e58dfe6f94eecfcb9a9c37d180d617e2720b16107f50`，由正式测试入口确认与 Cargo 产物字节一致。逐轮退出码、样本/源码/程序摘要、负载门槛、最小/中位/p95/最大耗时与资源观测保留在私有 `desktop/.local/perf-stability/`；不将私人原文或完整日志上传 GitHub。首次空闲门槛失败记录继续保留，不能用后续成功记录覆盖。

后测程序 SHA-256：`20eef8047d085c464957aa548f33f75dda46829daa29a4e7c2151b66c99afcf2`，同样经过现有测试入口核对。编译输入为同一父提交加本轮改动；两个程序的不可变副本、逐文件源码摘要和完整样本继续保留，主线后续合并不能自动扩大本轮测量适用范围。

分位数采用 nearest rank；n=15 的 p95 即该组最大值，只说明本组尾部，不能推断长期分布。每次读取事务提供该进程内的一致数据，跨进程另核对结果摘要与索引身份。

## 尚未签收

当前日常 Windows 窗口无响应且由另一对话管理恢复，本轮没有控制、重启或替换它。因此还缺实际输入→IPC→结果渲染、预览切换的窗口计时，以及同步/OCR 自然并行时的完整质量与资源验证。本轮不强制全量同步、重建或 OCR 来造场景。

没有约定的产品性能门槛，不能把数据取得、局部改善或单元测试通过说成达到统一体验指标。#6 仍保持打开；后续验收应复用本轮数据身份、案例与边界，补足实窗/并行场景，不能重复把 #4 的功能测试数字相加为新性能结论。
