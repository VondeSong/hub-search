## 导出后遇到连接故障和版本变化

沿用上述同一真实任务。两份成果已导出，在后台测试进程中让模型连接不可达。约 133 秒后本轮报出提供方连接错误。已有答复、计算记录、导出回执和两个文件的哈希均经回读确认。

正常退出 Hub 并启动新进程，从同一对话点「继续调查」。期间笔记版本发生变化，系统拒绝以旧版的第 14,000 字符为起点。该轮只解释原因，没有新原文。随后明确按当前版本补读，从第 0 字符读至第 2,000 字符，得到可定位的引文。覆盖记录保留两个版本各自的阅读范围。两轮恢复共新增一条失败说明和一条引用新版本的答复，分析、导出回执及业务动作均无新增。再次核对两个导出文件的哈希，均与原回执一致。

远端实时取件、真实缺公式缓存的工作簿、接近上限的容量和其余故障组合仍按 #58 跟踪。资料库界面一度显示连接未恢复，本轮使用已授权的本地资料。实窗截图留在会话，真实原件、报告、导出副本和回执留在本机忽略目录。

### GitHub 评论只读回查补验

复用 Hub 曾正常确认发布的真实验收评论。从日常库读出原动作的目标、确认正文和原回执，以现有授权调用 Hub 的同一只读回查路径。12.92 秒后返回同一动作、评论编号、URL 和正文哈希。本地原动作和回执逐字一致。另通过 GitHub 分页回查，确认同一动作标记只出现一次。 [原远端评论](https://github.com/VondeSong/hub-search/issues/14#issuecomment-6935725889)

整改回查判定。旧逻辑只对正文完全相同的评论去重，因此另一条正文不同但复制了动作标记的评论可能被漏掉。现在先要求动作标记唯一，再核对确认正文、有效评论编号，以及该编号对应的完整 Issue 链接。任何不一致都保留未知。10 项原生定向检查通过，包括原有未知禁止重发及新增回查判定。常规套件中的两条联网用例默认跳过，本轮单独运行其中的真实回查并通过。

本轮使用已发布评论验证真实服务上的恢复读取。仍缺首次发送时实际发生回包丢失的现场。按文件名额外核对了日常库中 14 份已缓存 XLSX，发现的 359 个公式格均有保存值，文件大小均未落在 7.21–10 MiB 的待补区间。此范围与此前扫描有重叠。
