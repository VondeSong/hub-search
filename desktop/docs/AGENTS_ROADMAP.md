## 1. 先用一个完整场景说明

以下是目标使用过程。第 5 节说明其中哪些已有基础、哪些尚未实现。

假设你在推进“项目 A”，资料散在 Craft、Obsidian、阅读收藏和任务里。

| 你做什么 | Hub 应怎样处理 | 你最后看到什么 |
| --- | --- | --- |
| 打开一篇资料，说“找相关联的资料” | 在获准范围搜索，读取原文，区分真正相关与仅同主题的内容 | 少量相关对象、关联理由、原文入口，以及没找到或无法确认的部分 |
| 接着说“结合之前的决定，看看下一步怎么做” | 恢复当前事项进展，查找适用的项目决定，核对变化和冲突 | 已知事实、仍缺的条件、建议步骤、需要你决定的选择 |
| 明确说“项目 A 以后采用方案 X，记住这个决定” | 保存决定的正文、项目范围、确认依据和版本 | 可查看、修改、停用或遗忘的一条项目决定 |
| 下次另开一个事项 | 按项目和当前问题取回适用内容 | 直接沿用有效背景，并能查看本次用了哪些规则和决定 |
| 让它整理标签、归档资料或生成闪卡 | 调用各业务已有流程，沿用该流程的审核、授权和写后核验 | 可审核的建议、实际保存位置或提交回执 |
| 工作需要等待某个结果 | 保存当前进展；你明确启用复查条件后，再按条件继续 | 等待什么、何时复查、已经取得什么、是否需要你操作 |
| 将模型切换为 DeepSeek | Hub 从自己的存储重新提供相同的有效上下文 | 新模型可继续同一项目，质量和耗时按该模型实际能力表现 |
| 后来改用方案 Y，或要求忘记方案 X | 更新有效版本，或清除记忆及其检索派生内容 | 后续只用当前决定；已遗忘内容不会因重启或重建索引自动回来 |

其中最基础的一步应当足够轻：**选中当前对象，输入一句委托，先拿到有用结果。** 不要求你先建立复杂项目体系、配置多个 Agent 或填写完整画像。

## 2. Agents 要覆盖哪些工作

这些工作由同一套事项、资料访问和执行机制承接，按任务采用不同技能。首版由一个主 Agent 对结果负责。

| 使用场景 | 典型委托 | 应交付的结果 | 主要建设位置 |
| --- | --- | --- | --- |
| 查资料与发现关联 | “这篇内容与我已有的哪些资料有关？” | 相关资料、依据、差异及覆盖局限 | 01A 调查可用性 |
| 恢复项目背景 | “之前为什么选这个方案，现在还成立吗？” | 当前决定、历史理由、变化与待确认条件 | 现有事项记录 ＋ 02 共享决定 |
| 学习与知识整理 | “整理这组材料，给出可审核的标签或闪卡” | 有来源的整理结果及审核入口 | 现有领域流程 ＋ 01B 模型迁移 |
| 推进具体事项 | “根据这些记录给出下一步，并执行已获准的部分” | 步骤、实际操作回执、未完成原因 | 现有动作系统 ＋ 各消费者验收 |
| 按约定继续 | “这个结果更新后再检查一次” | 条件变化后的复查结果或必要提醒 | 保留现有条件能力，迁移后复验 |
| 复用工作方法与成果 | “沿用上次的方法处理新材料” | 同一正式技能版本、可追溯的成果引用 | 01B 迁必要技能，03 完善共享管理 |

生活、知识、项目等可以成为观察视角或技能组合。只有确有独立权限、独立上下文或可证明的并行收益时，才进一步拆专业 Agent。

产品体验参考对象旁助手的入口形态：从正在看的内容发起工作，再回到持续保存的事项。界面入口和长期工作使用同一套 Hub 服务。这里规划的是 Hub 自己的能力，不以复刻 Notion/Craft 的内部实现或全部功能为目标。

## 3. 先分清“资料、项目、事项、记忆、技能、成果”

| 概念    | 用普通话解释             | 例子与关系                                  |
| ----- | ------------------ | -------------------------------------- |
| 原始资料  | 你已有的笔记、阅读、任务和附件    | 由 Craft、Obsidian、阅读和任务模块管理；Agent 按授权查阅 |
| 项目    | 一组事项共享背景的明确范围      | “项目 A”；由你创建或选择，可显式关联文件夹、目录或任务清单        |
| 事项    | 你托付给 Agent 的一件具体工作 | “比较 A/B 两种方案”；保存目标、进展、问题和继续条件          |
| 一次运行  | Agent 为事项执行的一轮工作   | 这轮搜索、读取、调用模型和交付；运行结束后，事项可能还在等待         |
| 共享记忆  | 后续事项可以复用的已确认规则与决定  | “项目 A 采用方案 X”；有范围、来源、版本和有效状态           |
| 技能    | 可复用的做事方法           | 怎样研究、归档或整理；技能说明需要什么能力和工具               |
| 成果与回执 | 工作产生的内容，以及实际操作的结果  | 调查报告、标签建议、归档位置、闪卡提交记录                  |

这几种内容的关系是：

> 原始资料提供事实 → 事项承载目标 → Agent 按技能工作 → 产生成果和回执。  
> 你明确确认的规则与决定，可进入共享记忆，供适用的后续事项使用。

### 第一版怎样划分记忆范围

只有两种共享范围：

- **个人通用**：你明确希望跨项目使用的规则或决定。
- **项目**：绑定一个稳定项目身份，只用于明确关联的事项。

一个事项可以不选项目，也可以明确关联一个项目。未关联时，只使用个人通用内容及该事项自己的记录；原始资料仍按来源权限读取。旧事项不会被批量自动归类。

项目关联用于组织背景。Craft 文件夹、Obsidian 目录或任务清单名称相同，不能自动认定属于同一项目；关联项目也不能增加资料读取权限。

### 什么会长期记住

首版保存**规则和明确决定**。你清楚地要求记住或修改，并已明确适用范围时，可以作为确认依据；Agent 推测出的偏好或建议先作为候选。只针对本次工作的临时要求留在当前事项。

完整聊天、每次模型总结和整份来源库不会自动进入共享记忆。已有事项记录继续保留；技能和成果的完整共享管理安排在后续批次。

### 运行、等待和失败时的体验

- **调查中**：已经保存且仍有效的材料能够先显示，最终报告继续生成。
- **需要决定**：明确告诉你缺哪个判断，以及决定后怎样继续。
- **等待结果**：保存进展，说明等待对象与条件；等待不占用模型运行名额。
- **超时、中断或失败**：保留可用进展、历史和回执，显示停止原因与继续入口。
- **来源变化或权限撤回**：旧内容过期或隐藏；后续继续时重新核对。
- **已完成**：满足本次委托的完成条件。一次模型调用成功、生成几张卡片或创建一条任务，都不能单独证明事项完成。

应用重启后保留事项和已核验进展。已经消失的运行标为中断；继续工作时建立新运行、重新核对来源和权限。取消会保留已发生的业务动作，结果未知的外部写入要先查询核实，再决定后续动作。

## 9. 记忆怎样生效、修改和遗忘

### 从“记住”到实际使用

1. 你明确表达规则或决定，并确定个人通用或项目范围。
2. Hub 保存内容、来源、确认依据和版本；同范围同主题沿稳定身份更新，重复请求避免创建等价副本。
3. 新正文写入并核验成功、来源仍有资格、索引已就绪后，条目才可用于后续事项。
4. 新事项先按范围筛选，再加载适用规则、查找相关决定，记录实际使用的条目和版本。
5. 你可查看、纠正、更新、停用或遗忘。

“已确认”和“当前可用”是两个状态。已确认内容若来源不可读、正文发生外部变化或索引未就绪，界面应说明原因，不能继续当作可用背景。

### 有冲突或外部变化时

新决定生效后，旧决定退出后续使用，历史成果保留当时依据。并发更新遇到版本竞争时明确提示冲突，首版不自动合并。

外部 Markdown 改动导致哈希不符时，暂停旧条目的使用资格，将新正文作为待确认版本；文件中的状态字段不能自行授予确认或权限。当前委托与长期规则有冲突时，按本次真实用户授权和 Hub 权限处理，实质冲突明确呈现。

### 停用和遗忘的区别

| 操作 | 后续使用 | 保留什么 |
| --- | --- | --- |
| 替代 | 只使用新有效版本 | 旧版本及历史依据按记录规则保留 |
| 停用 | 停止提供给模型 | 保留可查看的历史 |
| 遗忘 | 清除共享正文、历史正文、索引、向量、缓存、派生摘要和未完成写入 | 保留不含正文的最小删除凭证，防止自动回流 |

原始笔记、原始聊天、旧成果与业务回执有各自生命周期，删除记忆不会自动删除这些数据。后台也不能因原资料仍在而自动重新激活已遗忘条目。

已有旧备份不能远程抹除。恢复时应用仍可取得的删除记录，并说明可能恢复旧内容的边界。正式接入与联合验收必须覆盖迁移、备份、恢复、重启和索引重建。

## 10. 模型、工具与技能怎样配合

一次工作由 Hub 组织：

~~~text
你的委托与获准资料
  → Hub 恢复事项，选择有效背景
  → 模型提出搜索、读取、建议或工具请求
  → Hub 检查范围、预算与操作授权
  → 正式工具执行，Hub 核对结果
  → 保存进展、成果和回执，交给你查看或继续
~~~

模型负责推理与提出下一步。Hub 负责权限、执行与实际结果判定。模型写出“已完成”不能替代保存成功、外部操作结果或业务核验。

调查从目标和来源概览开始，按需要继续搜索、精确读取或核对反例。首轮命中只是候选；模型可以在原授权和预算内调整查询，Hub 每次重新检查访问资格。原文引用、模型推断、用户决定和实际回执分别保存，资料没有记载的实际进展保持未知。

### 模型可替换，需要迁移哪些东西

01B 要统一请求和结果、工具请求、结构化输出、错误、限流、取消、超时、用量及能力检查；同一套预算和排队服务所有模型消费者。Codex 保留为可选适配器，DeepSeek 通过直接 API 适配。

生成模型与嵌入模型分别管理：切换生成模型无需重建记忆；更换嵌入模型时，才按索引版本重建。不同模型可取得相同的有效背景，回答质量、措辞和耗时仍由实际能力决定。缺少指定工具、结构化输出或推理档位时明确提示，不静默替换。

### 业务操作与自动继续

| 工作 | 必须保留的规则 |
| --- | --- |
| 标签 | 沿用定义、待审核建议与确认流程，写后回读；来源或规则变化使旧建议失效 |
| 归档 | 显示实际落点与回执，沿用幂等和恢复；未知或部分成功先核实 |
| 闪卡 | 区分生成、审核、提交和用户接受，保留来源；生成成功不等于学习完成 |
| 任务及其它动作 | 逐项接入正式业务入口；保留各自状态与实际执行依据 |
| 条件继续 | 用户明确启用已知来源/回执变化或约定复查；手工操作优先，复用同一取消路径 |

界面区分待处理、已提交、已核验、部分成功与结果未知；取消或重启后，仍以实际操作结果和回执决定后续动作。

条件继续沿用旧 AG-04 限制：默认关闭；约定复查限未来 7 天内一次；每次委托最多 3 轮、7 天到期、同时最多 10 个条件，整库自动运行最多 10 轮/滚动 24 小时。每轮仍受 quick 的 120 秒和 3 次模型调用约束。没有依赖变化或到期就不调用模型；自由文本“等一等”不自动建立触发器。

来源失效、权限或决定变化、需要你判断时暂停。自动调查沿已有 Hub 内展示提醒，不自动取得业务写入权限，也不承诺应用未运行时的通知能力。
