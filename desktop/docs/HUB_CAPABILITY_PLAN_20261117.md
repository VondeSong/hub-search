## 1. 结论与产品定位

Hub 应成为围绕个人知识资料的工作助手：**找到资料，读懂图文和表格，结合历史决定进行研究，必要时实际计算，形成可追溯的成果，并在已有授权内完成保存或业务操作。**

保留 Codex 对知识工作有价值的能力：自主选择工具、连续追问、公开进度、网页研究、应用连接、脚本计算、文件产物、合适场景的委派、技能、记忆和失败后续做。重点补 Hub 的来源范围、版本、引用、材料覆盖和成果回库；这些是产品本身的职责，不能只依赖模型自觉。

不建设代码开发工作台：Git 分支/PR/代码审查/测试部署/IDE 调试不是产品主目标。但“不是编程产品”不构成禁止脚本的理由。对账、去重、单位转换、表格合并和图表生成需要实际程序计算；用户表达业务问题，Hub 负责选择分析工具和交付结果。

能力对齐的目标是“选定知识任务能完成、过程可信、成果可继续使用”，不是工具数、图标数或开关数相同。模型、推理强度、提示、材料、运行环境、工具权限和交付管理共同影响结果；同模型不等于同能力，限制工具也不等于直接降低模型推理参数。

### 2.2 我的失误与纠正

1. **把总目标收缩成局部接入，然后用“已完成”收口。** #14/#56 的限定成果有证据，不能否定；但没有同时把用户关心的全部能力给出明确去向。“本轮所选范围完成”的工程说法没有回答“Hub 现在到底缺什么”。这是规划与表达的责任，不能归因于用户没有继续追问。
2. **先按工具分类开发，后按真实业务补洞。** GitHub 评论方便证明写工具链路，但不足以代表知识库阅读和保存；短脚本计数不足以代表表格分析；预览有图片不足以代表模型读图。测试入口选得可执行，却没有一开始覆盖完整用户旅程。
3. **混用了接入、验收、质量和平台四种状态。** 一个工具已接通、一个案例通过、Windows 通过、整个产品可用不是同一个结论。单元测试多不能抵消关键真实场景未验收。
4. **缺口散落，文档过多且“当前”入口陈旧。** 总路线表还突出早期阶段，最新限制藏在不同评论中；未按“必须补齐／主动舍弃／明确延期／未验证”建立统一账本，导致每次只能再建议一项。
5. **把已有范围未验证和产品新目标混在一起。** 某项可以不是 #14 接入阶段的缺陷，但仍是知识库助手的必备欠账，不能因旧 Issue 已关闭就只称可选扩展。反过来，已有图表、记忆、恢复能力也不能因当前案例没用到就说完全没有。

纠正方式：保留历史事实和有效成果；#14/#56 的首屏明确“限定接入/展示完成”；#58 持续跟踪完整化，既不靠重开所有旧任务重做成果，也不靠新建事项把原承诺消失掉。后续若发现本期必需能力没完成，继续整改；若必须减少承诺，要明确改变了什么和损失什么，不能自行改成“扩展”后关单。

## 3. 统一状态与范围规则

每项能力同时记录两条轴，避免一个“支持”掩盖问题：

- **产品决策**：核心必备、受控保留、明确延期、不纳入产品。
- **工程证据**：已实现并有限验收、已有实现待专项验收、部分接通、明确缺口、运行端支持未证实。

“已验收”必须附版本、平台、来源类型、任务和限制。2026-11-17 规划时仅做文档、代码和 GitHub 核对，没有重跑下述历史测试；2026-11-18 的实施与实测以首屏链接的验收记录为准。没有证据的能力保持未知，不用未知推断不存在。

平台分开：Windows 为当前新能力主线；Android/VPS 由 #32 管理运行位置与传输。手机不需要本地运行 Python，但必须能准确说明任务在哪执行，发送获准材料，查看/取回成果，并在断网或重开后保持真实状态。桌面进程活着不能充当云端持续执行证据。

## 5. 取舍要讲清实际损失，不能把限制说成没有代价

| 决策 | 保留/替代方式 | 主动接受的损失 | 将来重新评估的条件 |

| 不建设软件开发工作台 | 脚本作为分析步骤，提供代码与运行记录查看 | 不能在 Hub 完整做仓库开发、PR 和部署 | 产品定位发生变化，而非偶尔需要一段脚本 |

## 6. 完整任务应该怎样工作

典型委托：“把这两份项目资料的差异和待核对项整理出来，算清数量，给我一份能继续改的表和报告。”

1. Hub 解析用户目标和已经允许的材料范围；检查正文、图片、附件和运行环境是否实际可用。无需为已授权的只读步骤重复询问。
2. 模型按需检索和读取，材料账本记录文档版本、已读段落、页码/图片、表格范围和缺失部分。找不到、读不清、未读取必须分别表达。
3. 简单计数复用短计算；复杂表格进入受控分析运行时。用户不用选语言，模型不能把“生成代码”冒充“执行成功”。
4. 计算记录输入快照、脚本、依赖版本、退出状态、标准输出、产物清单；数据质量问题保留原行及处理规则。来源不直接修改。
5. 答案引用来源位置；图表、表格、报告各自有稳定身份和版本。用户说“把口径改一下”时修订同一个成果，旧结论标记过期，不另造无法关联的文件。
6. 用户要求保存或发送时，根据已授权的目标和内容执行；超出已有授权才补必要确认。失败或响应未知先核对，不能再次盲目发送。
7. 停止或重开后，呈现已完成步骤、当前产物、未完成项和待核验动作；继续时核对来源版本，只重做受影响部分。

Hub 不应把所有配置都变成用户任务。默认从已选资料出发，优先现有 Hub 工具；需要网页、外部服务或新材料时说明具体收益和新增范围。允许的计算与只读处理由助手自主决定；能力缺失要在执行前或发现时明确报告，不让用户看几分钟“思考中”后才知道根本没有相应运行环境。

## 7. 实现方案：复用已有基础，补成完整链

### W1：图片、PDF 与材料覆盖

- 优先打通现有飞书来源图片：从来源稳定身份、缓存/获取、版本/哈希，到可选图片授权、实际像素发送、页/图位置引用、历史回读和撤销。先修链路，不能只增加 2 张/256 KiB 上限。
- 长文图像按需选取、分批处理；保留原始分辨率与实际发送分辨率，不为了塞进字节预算静默压坏工程图小字。原图下载/压缩/裁切失败独立说明。
- PDF 复用现有提取和渲染：有文本先定位，再读取相关页面图像；扫描件有 OCR 与视觉不确定性；不把 OCR 文本当像素阅读证据。页码、文本坐标和引用属于同一版本。
- 附件 manifest 记录媒体类型、来源对象、页/图/表位置、可读状态、实际读取覆盖和失败理由；不直接将预览 URL 或网络凭据放进模型上下文。
- 验收出口：真实飞书图文和真实 PDF 两种输入都形成“可选→实际读取→回答→定位→重开”的完整链。缺其中一种不能只以另一路径通过关闭 W1。

### W2：受控数据分析环境

- 保留 `hub_compute` 处理小任务，不把所有计算升级成大工作区。新增分析执行路径使用可准备、可检测的固定 Python 环境；pandas、表格读写和绘图库按实现时兼容资料选定固定版本，不继承 Codex 私有 runtime 路径，不宣称本次已经装好。
- 运行前检测依赖和平台；依赖准备与模型计算分开，默认不让脚本任意联网安装。环境不可用时明示，不能静默降级为模型心算大表。
- CSV/XLSX/JSON 输入保留行列、编码、空值、重复键、单位、日期、公式及缓存值来源。首期 XLSX 明确只读公式/缓存值，不执行宏、不承诺任意 Excel 公式重算；缓存不可信时标记并拒绝用其作确定结论。
- 必备操作：筛选、分组汇总、去重、两表关联/差异、日期/单位标准化和异常行清单。用户问的是业务问题，算法与统计口径应在成果中解释；不默认推断因果或运行任意复杂预测。
- 授权文件副本只读，输出单独目录；资源限制、超时、取消、输出截断和依赖缺失有明确状态。运行身份绑定输入、代码、环境和产物哈希，能复算与追查。
- 规划容量档位：基本档目标 10 MiB 文本表或 5 万行、XLSX 10 个工作表；分析目标最长 120 秒、2 GiB 内存，输出总量目标 50 MiB。**这些是待基准验证的设计目标，不是当前已支持数字**；真实代表数据须覆盖小样本和可用的大样本。执行前固定实际承诺档位，无法达到要记录瓶颈与影响，不能悄悄改验收口径。
- 复用现有图表版本/依赖失效合同，拓展通用表格数据绑定。首期必备 CSV/XLSX 结果、PNG/SVG 图表；交互仪表盘和任意绘图代码的内联执行不列为出口。

### W3：成果交付与保存

- 统一成果清单：标题、类型、稳定 ID、版本、来源、生成运行、真实路径/对象、可预览/下载状态和有效性。正文中的“已生成”必须能对应真实可打开产物。
- 报告首期 Markdown/PDF，数据首期 CSV/XLSX，图表 PNG/SVG；PDF 要实际渲染核对分页、中文、表格裁切和引用。DOCX/PPT/视频不混进首期承诺。
- 源数据变化后旧结果能查看历史但不标为当前；修改口径产生新版本，关联旧版本与重算。失效内容能否展示继续遵守现有授权规则，不能为了历史可读泄露撤销材料。
- 复用 Obsidian/既有来源的预览、确认、版本冲突、结果未知核验和索引；新工作区产物不自动进入原库。上传、发送和保存是不同动作，各自有回执。
- 新增交互先更新现有 Sites 原型，再按实施授权落桌面；本轮只定合同，不制作新 UI 或发布原型。

### W4：应用与浏览器用于知识任务

- 分清三个层次：工具连接可用、具体来源内容可读、业务动作完成。GitHub 通道继续保留，但不作为知识服务验收替身。
- 首个目标明确选择既有飞书知识来源，先利用当前同步/读取链补正文和附件；如果账号的正式 Apps 确实提供所需能力，再接适配。不能承诺飞书必定在 Codex Apps 目录中，也不因连接器登录过期伪报 Hub 图片链已修复。
- 已有 Craft/Obsidian 等来源保留独立权限与版本。MCP/Apps 返回的通用文本若没有版本合同，引用应标明抓取时间和可回读位置，不冒充版本化原文。
- 公共浏览器保留现有导航/快照/点击，增加**具体资料文件**的受控获取出口：显式来源、重定向/下载响应核验、类型/大小限制、来源文件进入 W1/W2，而非开放任意浏览器下载和脚本执行。
- 单一 origin 下页面所需跨域资源、登录页、动态请求不支持时要说明。现有 GET/HEAD 限制会阻断部分合法网站，也不能保证远端 GET 毫无副作用；不将其包装成通用浏览器无损替代。
- 登录态知识服务优先官方连接器；个人浏览器接管、表单提交和任意网站写操作明确不在本期。没有可用接口的资料获取会受限，这是已接受的范围损失。
- 写入优先复用现有 Hub 业务动作，不为每个连接器重造一套审批，也不把每次只读查询弹成确认。新写操作须明确对象、允许字段、动作身份和核验能力；无法回读则保留未知。

### W5：研究覆盖、记忆、长任务与恢复

- 在现有来源证据基础上统一覆盖账本：候选总数、实际读取的文档/段/页/表、重复区域、缺失/拒绝、答案引用范围。“只找到了这些”不能写成“全部只有这些”。
- 长上下文保留用户目标、关键决定、材料版本、重要中间产物、未完成项和未决副作用；压缩摘要与可回取原证据分开。检索补读不能越过授权，旧记忆不能覆盖当前明确指令。
- 同一事项按检查点继续，保留已完成且仍有效的产物；来源变化只重做依赖步骤。取消、失败、暂停、完成分别记录；未收到外部写入结果时先核验，不能重发。
- 工作区与冻结材料额度、子代理与冻结 Token 额度的现有限制先保留。新分析路径必须进入可计量账本；未能完整计量时明确拒绝该组合，不能为“能力更多”绕过用户额度。
- 本期保证显式继续与正确恢复，不承诺应用退出后自动跑、断电后原进程恢复或无限长任务。现有业务委派不足暂不扩：先证明主代理能完成，避免把多代理当质量保证。

### W6：能力可用性与公开工作过程

- 扩展已有每轮能力记录，形成统一查询：能力、平台、运行端、账号/连接、依赖就绪、授权范围、容量档位、不可用原因、成果类型和最近验证版本。由执行端实际检测，不硬编码一串“支持”。
- 每轮开始绑定能力快照，执行时继续核对撤销/目录/版本变化；能力展示可由同一事实生成，不能另维护一份永远显示可用的前端表。
- 公开过程继续复用 #56：操作图标表示动作，服务 Logo 表示真实服务，favicon 表示真实站点，子代理头像来自真实身份。没有事件就没有相应“已完成”。
- 新增“读取图片/页面”“分析表格”“运行计算”“生成文件”“保存/发送”语义；展示部分失败、重试、产物入口与引用，而不是把内部 JSON 当默认进度。
- 只展示公开摘要与活动，不要求隐藏原始推理。更接近 Codex 的外观不列为模型质量验收。
- 可读性不能因复刻浅灰样式而忽略：#56 已记录辅助文字对比度约 2.8:1，未达到全面 WCAG AA；新活动需核对实际字体/背景下的对比度、键盘状态和窄窗布局。沿用现有设计完成必要修正，完整系统 DPI/主题/触屏矩阵仍由 #31/#13 对应出口管理，不冒称已验。

### W7：统一联合验收与回归

采用第 9 节场景及故障矩阵，在日常真实资料库验证；共用执行只计一次。每个能力先有预期，再运行、复核、整改和回归。最后统一生成报告、截图索引、能力矩阵更新及 GitHub 完成记录，不每跑一个小例子就让用户决定下一项。

不承诺未经估算的日期或工时。新运行时准备、来源附件能力、账号可用性和实机时段会影响耗时；以出口而非“代码写了几天”判断完成。

| 资料撤销、删除、版本变化 | 停用旧证据/产物，指出受影响部分，不能越权续读 | 授权/版本检查、实窗结果 |
| 账号过期、连接撤销、工具目录变动 | 不换账号、不自动扩大授权；保留可继续步骤 | 预检、真实错误/恢复记录 |
| 图片过大/模糊、PDF 无文字、表格损坏 | 明确可读范围，允许补读/调整；不编造识别结果 | 实际输入、解析日志、回答 |
| 脚本超时、缺依赖、输出超限 | 保留失败和已产物；可解释地调整再执行，不装未知依赖 | 运行回执和产物清单 |
| 取消、网络断开、进程退出 | 准确终态、检查点、无重复业务副作用 | 进程所有者、事件、持久记录 |
| 保存/发送成功但回执丢失 | 先核对远端，未知不自动重发 | 动作身份、远端查证 |
| 额度/磁盘不足、未知计量 | 已有成果保留，拒绝不支持组合；未知不填 0 | 分项计量和错误 |
| 流式乱序/迟到、历史大量事件 | 顺序/终态稳定，部分失败可见，超过展示限额有说明 | 定向事件回归与真实长任务 |

协议负例可用离线夹具，但不能当真实资料业务成绩。真实环境不通过破坏源数据、强杀用户实例或注入错误业务内容来凑故障；采用可控取消、撤销测试授权、只读异常样本以及非生产协议回放，逐项注明证据类型。

## 10. 怎样判断比以前强，是否接近 Codex

**已知事实**：#57 的相同题目旧 Hub 累计 341.609 秒、新 Hub 355.555 秒；每题每版一次、先旧后新，受缓存/服务波动影响。这个结果不支持“全面提速”，也不能仅凭一次耗时判稳定退化。新增能力扩大任务范围，未证明模型本体更聪明。

后续采用两类独立对照：

1. **版本回归**：实施前冻结 Hub 基线，同材料、题目、模型、强度、授权策略和合理等效缓存条件比较。确认原来能做的仍能做，新增能力不是以基本问答变差为代价。
2. **产品能力对照**：Hub 与 Codex 使用同样可访问的材料及明确目标；记录实际工具/运行端差异。如果 Codex 自动具备文件分析而 Hub 没有，该失败就计为能力差距，不能把问题改成只有文字计数。另设等工具条件的子对照分析运行策略，但不替代真实产品比较。

每题记录：是否完成任务、重要事实准确性、引用可回查、材料覆盖、算数/表格正确、产物可用、用户额外操作次数、首反馈/总耗时、真实用量和未知项。引用匹配并不等于结论推导正确，需独立检查结论是否被原材料支持。

质量硬门槛：无伪造工具/已读/保存事实；重要数值与确定性复算一致；关键结论有来源或明确推断；未授权源内容不变；重复操作无重复写入。体验与性能目标：正常任务不需用户反复配置工具，不出现无限等待；目标场景至少两组真实材料，关键对照交替顺序重复三次，报告分布和失败，不宣称小样本百分比是普遍提升。

若当前无法获得同条件 Codex 产品运行，就明确记录未完成对照；#58 的产品对照项不勾选。可独立完成 Hub 实施与功能验收，但不能宣布“达到 Codex 水平”。
