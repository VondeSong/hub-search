# Hub 洞察交接文档

适用范围是 Hub Windows 桌面端「洞察」工作区，依据 2026-11-22 主线源码 `3382d03`。面向需要重新设计界面、接手开发或编写验收用例的人。桌面端使用本机同步资料和真实助手，工作台站点使用浏览器中的示例数据。

## 1. 洞察解决什么问题

用户从已有笔记、任务或分析里看见一条值得留下的判断，例如「图纸字段在纸面已经核对，仍缺实机验证」。洞察把判断和出处一起保存。以后即使来源变化、有人纠正或换了一轮分析，也能回看当时怎么判断、依据是什么、现在要不要修订。

贯穿整个工作区的四个对象各有用途。

| 对象 | 通俗解释 |
| --- | --- |
| 原事项 `Work` | 一个可以继续的工作台账，保存问题、资料权限、运行历史和预算。一次事项可以分析多轮。 |
| 已发布成果 `Delivery` | 助手某一轮交付的固定结果，带当时读取的材料。这是保存候选时要核对的出处。 |
| 候选发现 | 成果中能逐条核对的判断。用户可以查看引文、检查适用条件，再决定要不要留下。 |
| 已保存发现 `Insight` | 用户留下的卡片。它和原事项相连，自己拥有处理状态、反馈、修订和历史。 |

例如，助手读了两份验证记录，输出了完整分析。用户只留下「第二套方案仍缺实机结果」这一条。稍后补进实机记录时，Hub 接着原事项核对，用户可以保留原判断并记录本次核对，或者采用新的判断。旧版和当时的依据会留在历史里。

## 2. 当前界面有哪些入口

从 Hub 全局左栏进入「洞察」，默认打开「发现」和「待关注」。左栏先选要做的事，顶部页签再筛当前发现的处理状态。

| 左栏入口 | 用户在这里做什么 |
| --- | --- |
| 发现 | 开始分析、导入已有成果、浏览已留下的发现。可切换卡片或列表与详情并排，也可专注看一条。 |
| 真实案例／更多发现示例 | 阅读 5 个基于公开资料整理的案例，区分出处和应用推演。可以把案例另存为可编辑的工作草稿。 |
| 阶段回顾 | 带着问题梳理一批记录，或按本月、去年同期看变化。可接续原事项，也可直接贴入文字。 |
| 关注主题 | 长期留下一个问题、想回看的变化和对应事项。在已有正式交付、权限和预算允许时，可以明确启用有限复查。 |
| 工作草稿 | 编辑本机草稿，或查看原事项产生的业务草稿与实际保存回执。业务草稿的复核、执行和写回走原事项。 |
| 处理记录 | 集中回看发现的保存、反馈、复核和状态变化，可回到相应发现。受限的历史内容按当前权限隐藏。 |
| 待复核、星标发现、发现视角 | 同一批已保存发现的快捷筛选。视角有「知识与工作」「生活与进展」「决定与变化」。后者还可打开「记录与回顾决定」。 |

### 一张卡片怎样读

| 维度 | 可选值 | 用户可以怎样理解 |
| --- | --- | --- |
| 处理状态 | 待关注、稍后、已处理 | 我想何时再看、这条有没有处理完。「稍后」可选日期，时间到了在重新核对列表时回到待关注。 |
| 依据状态 | 依据已核对、待复核、来源不可用 | 现在还能不能看到和使用依据。「已核对」表示所用依据通过当前检查，结论仍有自己的适用条件。 |
| 星标、关注、视角 | 星标可独立开关，关注可取消，视角可修改 | 它们分别回答值得收藏吗、还希望继续跟这个判断吗、从哪个角度归类。关注主题的复查日程在主题中另行设置。 |

「已处理」和「待复核」可以同时出现。比如用户上周已处理一张卡，这周原笔记被修改，卡片应该提示依据变化，原处理状态仍有意义。卡片上的标题或摘要、依据数量和版本有现有字段可用。资料不可访问时，列表保留发现身份和可展示的处理状态，正文、引文和受限历史一起隐藏。

列表支持按事项、近 7 天／30 天、依据状态组合筛选，也可以搜索发现正文、关联事项、引文和已读摘录。搜索与计数基于当前已载入的数据，有「加载更多」时可继续翻页。每次列表查询最多返回 200 条。详情的上一条／下一条沿当前筛选顺序走。

## 3. 从资料到一条可回看的发现

### 开始发现

1. 点击「开始发现」，选 1–32 份明确的本地文字笔记。可填问题，也可以留空使用默认问题。预览笔记可以先看原文；接续时，新旧资料合计仍最多 32 份。
2. 如果想找过去的经验，先选当前资料，再明确允许查找哪些本地 Craft 或 Obsidian 库。系统用输入的线索词或从当前笔记提取的词找候选。可先读候选原文，只有明确加入的候选才进入本轮分析范围。
3. 点击开始时，桌面创建或接续原事项，沿用真实助手的模型、权限和运行预算。运行中可停止。停止或失败后可回原事项，或在允许时继续本轮。单纯打开页面、搜索、查原文和刷新结果都不启动模型。
4. 助手正式交付后，系统检查是否有可保存的结构化发现。完整回答可在结果区或原事项回看。无法核对的候选展示具体原因，没有合格候选时显示空结果。
5. 用户展开引用和共同背景，确认直接依据、分析方法与适用条件，再点「保留这条发现」。保存过程重新检查在用的原文和权限，成功后列表才出现卡片。

「从已有分析导入」是另一条入口。用户先找原事项，再选一轮已发布成果，逐条挑选可保存候选。它复用相同的引用检查和保存逻辑，全程只读取现有成果。更新已有发现时，候选必须来自该发现的原事项。

### 从判断继续到下一轮

- **看依据与完整工作。** 「发现与依据」显示保存时的精确引文、共同背景、方法、采用过的用户补充和内容版本。「查看引用原文」会按当前访问权限和版本重新读取。「原事项」打开当前 Agents，并带到同一个 `workId`。
- **补充与纠正。** 选择「事实或关联需要纠正」时，已保存的反馈会让发现进入待复核。选择「现在不需要」只留下用户反馈。「按补充继续核对」会把明确勾选的纠正送进原事项，并在执行条件允许时开始分析。运行完成后，用户还要显式选择新成果才能更新卡片。撤回纠正会留下历史，并重新检查曾使用它的内容。
- **加新资料复核。** 「加入后续记录并核对」带着旧判断接续原事项。「维持判断并留记录」保留旧文字，保存本次比较和新依据。「采用这次修订」使用本次候选的新正文。两种方式都沿用原发现，保留旧版本及处理历史。旧依据或共同背景失效时，系统可要求重新核对或改用完整修订。
- **表达替代关系。** 可以手动关联一条新发现替代旧发现，应用前需要明确确认。两条记录与历史各自保留。修订同一条发现和建立两条发现的替代关系，是两种不同操作。

### 两个「找旧资料」入口的区别

| 入口 | 查询范围和行为 |
| --- | --- |
| 「开始发现」里的历史资料查找 | 在这次明确允许的 Craft／Obsidian 库里按线索找候选。查看候选是检索行为，加入后才进入分析。 |
| 更多菜单里的「寻找旧知识」 | 先选择一个原事项。可直接做关键词检索，也可选「按含义与用途核对」或核对任务完成状态。后两种先准备问题与当前明确授权的资料，再进入原事项由用户发起分析。 |

任务状态核对需要明确选定的任务和说明笔记。它分别描述计划、纸面／原型验证和实际完成，缺少历史时保留未知。任务写回走原有业务确认流程。

## 4. 阶段回顾、决定和定时复查

### 阶段回顾

「直接提问／开放探索」是默认入口。用户也可以选择「本月回顾」或「对比去年同期」，再确定日期范围。「关注主题」是帮助表达问题的可选项。真正能用哪些记录取决于这次选择的原事项及其授权。贴入的记录会保留原文、性质、时间和版本，界面区分本人记录、转贴、引用或性质未明确。

「保存范围，准备回顾」保存这次问题和材料。进入助手明确开始后才运行模型。有些回顾可以直接用文字回答，有些会产出可保存的发现。金额或次数由模型提出可回看出处的候选，程序核对字段、原文位置、日期、归类、去重和覆盖，再做计算。资料不足显示「资料不足」，确定为零才显示零。两期不可比时保留能确认的数值。共同出现、用户自述和模型推测在结果里保留原来的性质。

结果页可回原回答和引用，可更正或撤回贴入材料。依赖这段材料的发现会进入待复核。单条观察绑定实际引用。像「本期全部记录」这样的集合判断还绑定范围、截止和覆盖。新增、移除或改动集合中的记录时，需重新核对相应结论。

### 决定与实际执行

「决定与变化」里的「记录与回顾决定」可保存当时的选项、理由、假设和发生日期。以后可以针对同一假设追加观察，回顾时明确选入其中几条。发生日期和补录时间各自保留，修改假设不会改写旧观察。主题、草稿和决定的「送入原事项」只准备这次要用的材料，仍要在助手显式开始。外部保存以原事项的实际回执为准。

关注主题可长期保存，但定时复查需要另行启用。当前为最多 7 天、3 轮，通过运行中的 Windows Hub 执行。成功进入本轮前还要经过原事项的权限、预算和历史交付检查。可以暂停。日程设置、暂停、到期及补做已到期一轮，都沿用助手已有的复查规则。发现卡片上的「稍后」只决定何时再显示，和这条执行日程无关。

## 5. 底层逻辑，接手实现时要保留什么

### 证据为什么可信，以及何时失效

前端通过桌面命令 `agent_investigation` 与本机 Rust 后端通信。后端按原事项授权读取本机已同步内容，打开、保存和更新时都可能重新校验。

1. **锁定出处。** 成果保存的是事项、运行和交付记录的身份，以及交付内容的校验值。候选还有它在本轮成果中的位置。另一轮回答即使题目相同，也有自己的出处。
2. **逐条校验。** 后端核对引文是否真的出现在当时读取的原文中，引用是否属于这次交付，来源现在是否能读、版本是否仍匹配。资料依据、共同背景、分析方法和用户补充分别记录。复杂附件、派生材料或共享记忆等依赖无法逐条确认时，候选会标为不可采用。
3. **区分变更和撤权。** 来源版本或方法改变时，仍可访问的发现可显示「待复核」。权限撤回、来源删除停用、原事项不可访问或备份尚未重新确认时，受限正文、引文和历史内容不会回传。同步更新、事项更新或回到窗口会让前端先清掉旧正文，重新校验后再显示。
4. **保存事务与恢复。** 每次写入带独立操作 ID 和预期记录版本。相同请求重试可查回原结果，旧页面不能覆盖较新的内容。同一正式出处只能绑定一条发现。结果不确定时先查原操作，再按原请求重试。备份恢复后要重新确认本机资料访问，远端最新状态由来源库核对。

### 存储和版本

| 本机记录 | 内容与用途 |
| --- | --- |
| `insights` | 发现身份、原事项、当前内容版本、记录版本、处理状态、星标及关注。 |
| `insight_revisions` | 每版的正文、依据与背景、方法版本、已采用补充及复核对照。 |
| `insight_origins` | 将原事项、固定交付与候选位置对上已保存发现。用于溯源和去重。 |
| `insight_events` | 反馈、处理、重新核对及其他操作历史。也用于检查写入是否已经提交。 |
| 原事项与 `agent_records` | 保留正式交付、回顾配置、文字材料、笔记本记录及对应版本。洞察复用这些对象和访问判断。 |

代码中的 `headRevision` 表示正文的最新版本，`contentRevision` 表示此刻正在看的版本，`rowRevision` 是用来避免覆盖他人或另一窗口更新的记录版本。星标等操作可以改变记录版本而不生成一版新正文。旧正文可以回看，本轮反馈和更新只对当前版本开放。

## 6. 交接验收与源码入口

重新设计时，至少用以下几条真实流程检查新界面。

1. **从材料到发现。** 用现有真实笔记开始，先预览，再发起分析。保存合格候选后，从卡片打开原文和原事项。资料不足时让用户看见原因。
2. **状态各自有效。** 用已有的状态和来源变化记录核对星标、视角与稍后的筛选，并检查「待复核」能否与「已处理」同时显示。
3. **从纠正到采用。** 保存纠正，明确选择反馈再开始核对。用户采用修订后仍可回看旧版与记录。取消或中断途中步骤时仍能从原事项接续。
4. **异常安全。** 用已经失效的来源、旧版本提交或重启后的未确认写入验收。检查页面是否隐藏受限内容、保留草稿和操作身份，并让用户知道怎样确认本次写入。
5. **回顾与主题。** 验证准备回顾只保存配置，资料不足能解释缺口。启用和暂停复查各有明确动作，可看见实际剩余次数。验收使用现有日常数据，避免向真实资料库写入测试内容。
