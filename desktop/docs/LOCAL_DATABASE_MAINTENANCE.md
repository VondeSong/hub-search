# 本地数据库物理空间回收（H14）

2026-10-12 续批已在数据库版本 69 的当前 native5 上重新执行并通过下述 19 项稳定序号与物理维护检查；新增子牌组和任务计数表仍由全表保留规则覆盖。正文的 native20、443 项和 32 项记录属于 2026-10-11 历史验收。当前交付见 [性能与架构续批](PROJECT_OPTIMIZATION_20261012.md)，未整理真实用户数据库。

当前源码已实现 Windows 离线空间整理、稳定序号迁移和可回退的文件切换。设置中的“释放闲置空间”先做只读预览；“安排下次启动整理”保存明确的维护请求，下次启动在任何业务数据库连接和后台任务启动前执行。没有待执行请求时，启动和普通清理不会自行压缩数据库。

空闲页是 SQLite 可以重复使用的空间，并不等于业务正文。2026-10-11 的旧只读样本约为 2.82 GB、空闲页占 95.22%；这仅描述该样本，不代表当前安装或其它设备的可回收比例。实际预览读取当前数据库页数、空闲页、主文件/WAL 大小和磁盘余量，成功后报告实际文件大小变化。

## 用户入口与取消

在设置中安排后，先结束同步或备份并完整退出 Hub，再重新打开。页面的“取消安排”用于撤销尚未执行的请求；整理期间启动过程尚未完成，这个页面不提供正在运行的取消按钮。

独立离线入口由同一个程序提供，参数必须严格使用以下格式，数据目录必须是包含 `craft-search.sqlite3` 的明确绝对子目录：

```text
<Hub 程序完整路径> --database-maintenance preview --data-dir <绝对数据目录>
<Hub 程序完整路径> --database-maintenance status  --data-dir <绝对数据目录>
<Hub 程序完整路径> --database-maintenance request --data-dir <绝对数据目录>
<Hub 程序完整路径> --database-maintenance run     --data-dir <绝对数据目录>
<Hub 程序完整路径> --database-maintenance cancel  --data-dir <绝对数据目录>
```

`request` 只安排批次，`run` 执行该批次或处理上次中断的恢复；这些参数不能与其它启动模式组合。运行期间可从另一维护进程调用 `cancel`：持久取消标记由实际执行者读取，备份、摘要检查和 `VACUUM INTO` 都有取消边界。取消发生在文件切换阶段时也恢复可用源库；已经完整提交的批次保持成功状态。

已有 Hub 或其它连接仍打开目标数据库时，Windows 排他文件句柄及 SQLite 排他锁会拒绝执行或切换。当前其它平台不提供离线整理，设置入口显示不支持状态。

## 稳定媒体身份和续行序号

被附件地址、最近保存位置或持久分页引用的 17 张表已改用显式 `local_seq`：

- `cloud_device_events`、`cloud_device_pending`、`cloud_maintenance_runs`、`flashcard_cloud_uploads`、`tag_content_scan_budget_history`。
- `reading_sync_records`、`reading_sync_pending`、`reading_copy_snapshots`、`reading_copy_pending`、`reading_media_manifests`、`reading_media_outbox`。
- `collection_property_updates`、`collection_x_outbox`、`collection_obsidian_exports`、`collection_library_destinations`、`collection_remote_copies`、`collection_saved_media`。

首次迁移将原隐式行号原样复制到新列，添加唯一索引并保存持久高水位；后续插入在同一事务分配新序号，删除后也不复用已提交的序号。业务主键、外键、索引和触发器保留，已分配序号禁止修改。保护触发器损坏时拒绝继续使用，不能仅凭安装标记忽略损坏。

独立模块在裸数据库连接上建立结构时，稳定序号入口仅在缺少公共元数据表时补建与主库一致的结构，并纳入同一保存点。未知表、安装错误或外层事务回滚会一同回退新建元数据、列、索引和触发器；已有元数据与保护标记不被覆盖。

保存原图、缩略图、附件 URL、最近保存位置及云维护分页的正式生产者和消费者均使用稳定身份。SQLite BLOB 读写所需的即时物理行地址不持久化；每次按 namespace/对象主键重新查找，压缩后仍能读取相同内容。

## 保留范围和离线流程

整理不会选择性删除业务或缓存表。完整数据库的架构对象、全部表、列、类型化单元格值和记录数都进入备份与校验；正文、媒体索引、待同步/删除事实、队列、已应用收据及部分完成的云恢复或维护 scratch 状态全部保留。新表和未知表也按完整表处理，不因名称含 `scratch`、批次尚为 `partial` 或属于派生状态而在物理整理中被清空。

1. 核对数据库和维护目录属于明确数据根，预留主文件与 WAL 总量的三倍加 16 MiB 空间。
2. 取得排他所有权，通过 SQLite 备份 API 保存一致备份，检查完整性、外键、架构及全表摘要。
3. 保留原始备份，在独立准备副本安装稳定序号，再生成 `VACUUM INTO` 候选文件；检查内容和架构一致。
4. 关闭 SQLite，重新取得 Windows 排他文件句柄，并核对源文件 SHA，拒绝替换在交接间隙发生变化的源库。
5. 将源库移到回退位置，再原子安装候选；重新打开并完成同样核验。取消、切换失败或中断时按已记录的文件身份恢复。
6. 保留原库、一致备份及诊断记录。恢复副本 SHA 或完整性损坏时停止，不覆盖现有候选或原库，也不静默使用损坏副本。

批次目录位于数据根的 `database-maintenance/<批次 ID>/`，包括 `consistent-backup.sqlite3`、`original.sqlite3` 及状态/验证证据。失败时可能额外保留候选和准备文件。成功与失败都不自动删除这些回退数据；后续清理由用户另行决定。

完整校验与压缩仍需读取全库、写入备份和候选。SQLite 读取较大的 TEXT/BLOB 单元格时可能物化整个单元格；兼容基线的 SQL 复制或类型转换也可能占用与该字段大小成正比的原生内存。这是显式离线操作的资源成本，不能从 Rust 流式处理推导整个进程具有恒定内存上限。
