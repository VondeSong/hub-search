# 全局标签审计断点续跑（v127）

Hub 保存进度和证据版本，Codex 分析候选，用户审核建议。此功能不运行内置 AI、不自动批准、不修改 Craft / Obsidian / 滴答标签。

## 怎样使用

继续使用标签治理收件箱的“复制全局审计任务”入口，将任务交给连接新版 Hub MCP 的 Codex。任务会先查断点；中断后再次发送同一任务即可继续。无需保持搜索窗口打开，也无需创建定时任务。

已保存的目录页会先被处理，不会因中断而跳过。候选建议保存成功后，完成状态和建议 ID 一起落库，不会因为回复丢失而重复提交。每轮默认最多扫描 5 页、深入 20 个标签和 10 组关系；剩余队列留给下一轮，这些是工作量上限，不是必须填满的数量。

没有新增审计面板：当前进度通过 Codex 的 `hub_tag_audit_status` 结果和每轮汇报查看，建议仍在原审核收件箱中。MCP 客户端若缓存了旧工具列表，需要重连新版 Hub MCP 后再使用。

## 数据升级与边界

- schema 49 → 50，只新增 `tag_audit_runs` 与 `tag_audit_receipts`，不改笔记和已有审核记录。
- 首次用新版打开实际数据目录（包括 MCP 访问）会自动迁移。建议先退出旧版并备份整个 Hub 数据目录。v126 不支持直接读取 schema 50；如需回退，恢复升级前备份，不要手改版本号。
- 本轮只在临时测试库验证写入、恢复和迁移，没有在真实库创建审计、提交或批准建议。
- MCP 工具总数 23：15 个只读、8 个可能写入 Hub；危险操作仍只有原来的两个内部关系操作。新增 `step` 不修改关系或来源标签，但 `record` 会保存待审核建议，必须有提交授权。

## 保存的内容

| 内容 | 作用 |
| --- | --- |
| runId / version | 定位审计与防止并发覆盖 |
| indexRevision / auditRevision | 索引版本及基于标签归属、文档元数据/内容哈希、任务文本的证据指纹 |
| 当前目录 cursor、已读标签、pendingCatalogPage | 恢复扫描，保留尚未确认筛选的目录页 |
| 候选 tagIds、reason、itemId | 保存单标签与标签对队列；标签对顺序和大小写不会重复建项 |
| proposalId / summary | 每个已处理候选对应的待审核结论；包括证据不足结论 |
| requestId / request hash | 同一步骤准确重试，不接受用同一请求号覆盖不同内容 |

`catalogScanned` 是读取的目录项数，`catalogReviewed` 是已确认筛选数，覆盖率按后者计算。`tagsAnalyzed/pairsAnalyzed` 是已保存候选结论的累计统计，不证明模型确实完整理解了笔记，也不代表这些建议已通过质量检查或人工批准。目录读完不等于所有标签都被深入分析。

## MCP 协议

### 读取进度

`hub_tag_audit_status({runId?, itemStatus?, cursor?, limit?})`：默认优先返回当前证据指纹对应的最近审计，没有则返回最近旧审计或 `run:null`。`itemStatus` 默认为 pending，可用 all / completed；每页最大 100，nextCursor 为空结束。

候选分页不是冻结快照。处理一项后 pending 队列会缩短，应重新取首批，不能使用处理前的数字 cursor 跳过剩余候选。查看历史时可以正常分页。

### 推进一步

`hub_tag_audit_step` 的 action：

1. `start`：传入 status 返回的 `expectedIndexRevision`、`expectedAuditRevision` 及稳定 `idempotencyKey`（例如 `global-tag-audit:{auditRevision}`）。已存在则恢复，不重建。
2. `scan`：固定读取并保存下一页 100 项。当前有 pendingCatalogPage 时拒绝继续翻页。
3. `queue`：传 `candidates:[{tagIds:[...],reason:"..."}]`，每候选 1 个标签或 2 个不同标签，每次最多 100 候选，每审计最多 2,000 个候选。必须来自本次已读目录。可 `candidates:[]`；`acknowledgePage:true` 明确确认当前页筛选完成。跨页关系可在双方读到后再加入。
4. `record`：传 `itemId`、`submitForReview:true` 和标准治理 `proposal`。标签范围必须与候选一致，索引版本必须匹配；Hub 生成 run+item 独立幂等键和生成器信息，原子提交建议与完成状态。返回 `recordedProposalId`，随后仍须预演检查。禁止再用普通提交工具重复提交此候选；`audit:` 键为断点协议保留。
5. `finish`：只允许目录读完、末页已确认、所有候选均有结论时标记完成。未完成时不调用即可安全暂停。

除 start 外，必须传 `runId`、最新 `expectedVersion`、唯一 `requestId`。网络结果不确定时原样重试同一步全部参数。重放返回当前断点，而非旧响应快照；同请求号的不同参数会被拒绝。版本冲突后先重新读取，不能盲目增加版本。

## 变化、失败与权限

- 标签数量不变但归属/名称改变，或文档标题、内容哈希、任务文本变化，也会改变 auditRevision。旧 run 标记 stale，只能查看；新 run 从头重新取证，不迁移旧结论为已完成。
- 指纹针对 Hub 已索引数据，不检查尚未同步到 Hub 的来源变更。
- 写入建议、更新候选与记录回执在同一 SQLite 事务内。任一步失败会整体回滚；重试不会出现孤立建议。
- 两个客户端拿同一 version 更新，只有一个能成功，另一个必须重读。
- 审计完成只代表目录筛选与候选结论已保存。质量检查阻断、证据不足、人工驳回都不等于“标签已优化”。
- 普通只读分析不授权持久化或提交；新建/恢复持久化工作及提交仍遵守用户意图。任何步骤都不授权自动批准、撤销或来源写回。
