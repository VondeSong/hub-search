# Hub 内容补标规划与验收

更新：2026-09-09。

当前测试包：`desktop/src-tauri/target/release/bundle/portable/Hub_0.16.122_assignment_edgecases_20260909_x64_portable.exe`（schema 61，31 个 MCP 工具），包含审核上下文及超长无空格摘要回退修复。此前测试包与验收记录保留在下文。

## 目标与边界

内容补标与标签关系治理是两条独立流程：

- 标签关系治理判断标签之间的 `related`、`alias`、`merge`、`parent_child` 等关系。
- 内容补标判断某个稳定内容实体是否应该增加一个 Hub 内部标签。

任何内容补标候选都不能伪装成 `hub.tag-governance.v1` 标签关系建议。Codex 只发现、取证和提交内容建议；用户在 Hub 内明确批准后，才增加 Hub 内部内容标签。不会修改 Craft、Obsidian、滴答或其他来源标签。

## 第一批实现

`hub_find_tag_assignment_candidates` 已提供受预算限制的只读候选发现：

- 目标标签必须已经存在，并应先经 `hub_tag_catalog` 核对。
- 支持 1–6 个短查询和明确的 `libraryIds` 范围。
- 排除已经带有目标来源标签或已批准 Hub 内部标签的实体。
- 多查询结果按稳定实体去重；取证接口按当前实体正文计算重复组，不把同一 Craft 父文档下的不同页面误认为重复。
- 最多返回 50 个候选，单候选摘要最多 800 字符，总摘要最多 20,000 字符。
- 响应分别报告命中、已有标签排除、重复实体和实际返回数量。
- 响应固定声明 `coverageClaim=candidate_discovery_only`，不把词法检索描述成完整全库分析。

标签属性页新增“复制 Codex 补标任务”。任务携带用户标签说明、本地父级和别名，要求 Codex 先明确资料库范围，首轮最多返回 30 个候选、补读 5 篇正文，并将结果分为：

- `recommend_add`
- `related_only`
- `out_of_scope`
- `insufficient_evidence`

## 第二批实现：审核闭环（数据库 schema 51）

- 标签详情的“内容补标 → 补标定义与范围”保存用户确认的定义、纳入条件、排除条件和已启用资料库范围。定义有版本锁，不能被旧窗口静默覆盖。
- MCP 新增 `hub_tag_assignment_definition`、`hub_read_tag_assignment_evidence`、`hub_submit_tag_assignment_proposal`、`hub_list_tag_assignment_proposals`、`hub_preview_tag_assignment_proposal`。不提供内容补标的 MCP 批准、撤销或定义写入工具。
- `hub.tag-assignment.v1` 逐实体保存建议，必须附精确来源、取证接口返回的当前哈希、定义版本、可逐字定位原文、判断理由、置信度和生成器。搜索候选的文档哈希不能替代取证哈希。
- Craft 精确到页面；Obsidian 精确到笔记；滴答精确到任务。仅使用已启用资料库中的当前文本，不自动读取附件或其他来源。
- 预演重新读取正文和定义，检查来源是否已有目标标签。正文、定义或状态变化都会使旧审核令牌失效；非 `recommend_add` 建议只能查看或驳回。
- Hub 审核区支持待审核、已批准、已驳回、已撤销，展示原文、理由、风险、定义快照及来源标签/内部标签的区别。
- 批准只写 `hub_content_tags`；撤销只删除该条内部关联。两者都排队更新索引，并刷新标签页、计数及搜索结果。索引失败会明确提示“审核已保存，索引等待更新”，不伪装成整个审核失败。
- 幂等键防重复写入；同一实体、正文版本、标签定义版本的重复建议复用已有记录（包括已驳回记录），不反复产生卡片。来源和定义变化后可重新分析。
- 已有标签目录、画像、比较、相关标签、标签搜索和动态筛选同时识别内部关联。

## 使用步骤

1. 在标签详情展开“内容补标”，确认并保存标签定义、边界和资料库范围。
2. 点击“复制 Codex 补标任务”，交给已连接新版 Hub MCP 的 Codex。当前仍是显式交接，不是 Hub 自动启动 Codex。
3. Codex 分批检索并取证，将建议提交到 Hub 待审核；返回 Hub 点击“刷新建议”。
4. 展开一条建议，核对原文和风险后选择“批准到 Hub”或“驳回”。已批准列表可以撤销内部标签。
5. 更新程序后需重启 Hub；如果 Codex 仍看不到新增 MCP 工具，应重新连接 Hub MCP。

## 第三批实现：按内容检查台账（数据库 schema 52）

本批是“单个标签 × 已确认资料库范围”的内容清单，不是一次性给全库匹配所有标签。

- 标签页新增折叠的“逐篇检查（可续跑）→ 复制 Codex 逐篇检查任务”。原来的关键词候选发现入口保持不变；复制本身不启动分析。
- 新增 `hub_tag_content_scan_status`（只读）和 `hub_tag_content_scan_step`（仅写 Hub 本地进度）。工具总数为 31；不新增批准、撤销或来源写入工具。
- `start` 将当前已索引的 Craft 页面、Obsidian 笔记、滴答任务定位固定为清单，不要求内容已经带标签。只使用用户确认定义中的已启用资料库；不会自动包含附件、图片或之后新增的实体。超过 100,000 项报错回滚，不截断后声称完整覆盖。
- 清单冻结的是定位，不是全文。`read` 按实际当前正文取证；`record` 再核对正文哈希、定义版本和来源。不同 Craft 页面分别处理。
- 默认累计预算为 30 个不同实体、15,000 正文字符；每次 read 默认 1,500 字符，单次最多 6,000 字符。补读和使用新请求 ID 的重复读取都计入字符预算；相同请求原参数重试返回回执，不重复扣减。预算不是 Codex 总 token 统计，也不约束其他通用读取工具；工作流禁止绕过。
- 状态分别统计 `unread`、`read`、`recorded`、`already_tagged`、`unavailable`，另列四种判断的 `decisionCounts`。来源不可用不冒充已分析，无可读正文不强造补标依据。
- `record` 只能关联当前已保存的独立补标建议，且 quote 必须出现在本任务实际返回的原文区间中。提交和记录是两次操作：提交后中断，可通过已有建议列表和同版本去重恢复，不需要重新建立审核卡片。
- `expectedVersion` 防并发覆盖，`requestId` 加请求摘要防止改参数重试；每次正文预算扣减、清单状态变化及回执在同一事务中保存。标签定义或资料库范围变化，旧任务只读。
- `finish` 要求没有未读或未记录项；`unavailable` 仍明确展示为未解决项。结束仅代表清单处理完，不代表完整阅读、语义判断正确、全库当前内容均已分析或用户已批准。
- 回执中若旧证据已变化或范围不可用，不再返回旧正文作为当前证据。状态响应保留已读哈希和覆盖区间位置，供断点恢复使用。

### 断点操作顺序

1. `hub_tag_assignment_definition(tag)` 读取已确认定义，再用 `hub_tag_content_scan_status(tag)` 查旧任务。
2. 无旧任务才 `step(action=start, tag, definitionVersion, idempotencyKey, maxEntities=30, maxChars=15000)`。
3. 从状态返回的 pending 首批取 `ordinal`，携带 `runId/expectedVersion/requestId` 调用 `read`。定向补读使用 `startChar`。
4. 用原有 `hub_submit_tag_assignment_proposal` 保存判断，再 `step(action=record, ordinal, proposalId, ...)` 关联台账，并预演建议。每次步骤使用最新任务版本。
5. 无未处理项时 `finish`；耗尽预算时直接保留断点，不 finish，不自动新建任务继续花费。

第三批的限制（已由第四批补齐）：当时没有预算追加界面。现在可在 Hub 确认追加后恢复同一任务；仍不能自动加额、悄悄重开已结束任务或沿用过期定义。

状态的 `stale` 检查定义和资料库可用性，不逐篇复核历史已记录建议。历史建议是否仍可批准，仍需独立调用补标预演接口；不能将历史统计当作实时语义验收。

## 第四批实现：进度与用户预算确认（schema 53）

- 标签详情“内容补标”中新增折叠的“逐篇检查进度与预算”。展开时才读取当前任务，手动刷新，不轮询、不启动 Codex。显示未读、已读未记录、已保存判断、已有标签、不可用、四种判断及实体/字符已用和剩余额度。
- “追加本任务预算”分别输入增加的实体和正文字符，先预览总额变化，再单独点击“确认追加预算”。不清零已用额度、不改变清单或定义范围、不生成/批准标签建议，不自动启动分析。
- 桌面专用操作为 `scan_status`、`scan_preview_budget`、`scan_apply_budget`，经既有 `tag_assignment` 命令调用；不注册为 MCP 工具，MCP 工具数量仍为 31。
- 确认绑定任务 ID、当前进度版本、定义及精确追加数。其他窗口推进任务、范围或定义变化、修改追加数都会阻止旧确认；重复发送同次确认只返回回执，不重复加额。
- schema 53 保存追加前后额度、进度版本、请求摘要和时间，更新额度、版本与记录在同一事务完成。界面展示最近 10 次追加；完整记录保留在本地数据库。
- 额度必须为非负整数且至少增加一项；每个任务累计总额不超过 5,000 个实体、5,000,000 正文字符。已经结束、定义/范围过期或没有未处理项的任务不能加额。
- “复制继续任务”绑定精确 runId，追加后重新读取服务器额度和版本，不另建清单。复制本身不开始分析。确认返回异常时界面清除旧预览，要求刷新核对额度及历史，不能盲目再加一次。
- 所有计量仍是本任务返回的正文字符，而不是 token、金额或全局调用额度。既有来源读取工具不受这张台账约束，交接提示禁止绕过预算。
- 入口沿用 apple-ui-design 的渐进展开、语义文字和原生表单焦点，不增加玻璃装饰或“全部分析完成”的误导百分比。

## 第五批：历史任务选择

- 在“逐篇检查进度与预算”展开后点击“查看历史任务”，可按当前标签分页读取历史。排序使用创建时间和任务 ID，同时间任务分页不重复、不跳项，每页默认 20 条。

## 第六批：用户确认创建新轮次

- 入口：“内容补标 → 逐篇检查进度与预算 → 新建一轮检查”。先配置实体、正文字符额度，再预览定义版本、资料库范围、清单数量和旧任务数量，最后单独确认创建。
- 新任务保留全部旧任务，不自动取消尚未结束的任务。创建本身不向 Codex 返回正文、不启动 Codex、不提交或批准补标建议；继续旧任务应追加原任务预算，避免重复读取成本。
- 预览复用真实清单构建器，但在保存点内回滚，不持久化临时任务。确认绑定定义、清单定位/标题、旧任务进度与额度；这些状态变化后须重新预览。清单不是全文快照，正文仍在实际读取时核验。
- 同次确认使用稳定请求编号，原参数重试返回同一任务；篡改参数或另用请求编号重复提交过期预览会被拒绝。失败或结果不明确时提示先查看历史，不盲目重复创建。
- 创建成功选中新任务，之后刷新、预算追加与复制继续任务均绑定此任务 ID。桌面命令新增 `scan_preview_new`、`scan_create_new`，未注册成 MCP 工具，数据库保持 schema 53。
- 沿用 hub-tag-steward 的人工审核边界及 apple-ui-design 的渐进展开、原生表单与明确状态，不增加自动批准或装饰性玻璃层。

## 第七批：完整预算追加历史分页
