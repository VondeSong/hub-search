# 资料库受控编辑接续核对

对应 #26，父模块 #35；2026-11-15。此次接续资料库剩余任务，先核对现有实现和主数据边界；不因统一入口将所有来源转换后写回。

## 已存在的基础

当前主线已有 `obsidian_edit.rs` 和 Agents 动作调用：对启用的 Obsidian Markdown 原件建立带库、文档、路径、文件身份、原始字节与 SHA-256 的快照，正文提议与原始文件分开。它不是 Craft/飞书/滴答的通用回写器，也不是资料库预览页已经有完整编辑器。

本地实现核对：

- 原文件保留为主数据，快照与提议不承担主数据职责；正文上限 48,000 字节，提议正文 1–12,000 字符。
- 文档必须属于启用 Obsidian 库；核对路径派生身份、排除目录、路径组件、原库范围和原件类型。符号链接、目录联接及越界路径不能通过该写入入口。
- 原 YAML 和 BOM 从快照保留；正文按原件换行方式组合；混合换行、坏编码、不完整 YAML 和超限内容明确拒绝，不静默替换或重建属性。
- Windows 的提交原语锁定原文件和祖先目录，对照路径、文件身份和原文基线。调用者仍需按现有动作机制先持久记录操作，再提交和回读；不能只调用 compose 就宣称保存。
- `sources::obsidian_open_url` 已支持原库、路径、章节和空格编码；打开文件仍由 Obsidian 负责，不代表 Hub 检测到了保存或完成索引刷新。

本轮新增显式忽略的真实只读检查：从已启用 OS 的两篇现有笔记读取快照，原正文不改地经过 split/compose，核对属性、换行、字节备份、哈希及文件身份。检查不会调用写入原语，也不会创建验收笔记。已在完整原生程序中显式执行并通过：两篇实际笔记的快照、原正文不改的组合、原字节备份、哈希与文件身份保持一致；没有运行既有合成资料夹验收，也没有调用任何笔记写入原语。

## 各来源推进边界

| 来源 | 主数据 | 本期可复用/接续 | 仍未完成 |
| --- | --- | --- | --- |
| 原生 Obsidian/OS | 原 Vault 中同一文件 | 现有打开、只读快照、带基线的正文提议和受控动作 | 统一资料库编辑入口的原型、真实用户修改到回读/索引闭环；不能用未改正文往返替代写入验收 |
| Craft | 原空间对象和块 | Hub 默认直接阅读；复杂内容按需使用派生阅读副本 | 目标普通文本块读取、块身份、基线、精确更新和结果未知恢复；渲染后 Markdown 不可直接逆写 |
| 飞书 | 文档对象和块；Wiki 节点另有身份 | 沿用当前只读正文与原文入口 | docx 普通块编辑适配；Wiki、表格、多维表格及权限独立，不能把 my_library 当 Wiki |
| 滴答 | 来源任务对象和字段 | 既有受控任务动作继续归任务模块 | 任意 Markdown 编辑投影到标题/正文等字段的范围、冲突与回读；勾选或删文件不自动等于任务操作 |

推荐采用现有 Obsidian 原文件作为首个可验收的编辑对象，Hub 阅读保持默认；其他来源先明确允许字段与结果状态，再接同一套提议、冲突和回执。这里没有选择迁移全部资料或创建第二套主数据。

远端块写前读取/哈希对比不能冒充来源原子条件更新。没有可靠版本前置条件时要限制并发适用场景；来源不可访问与确实删除分开，超时先回读，不自动重放插入。备份对象继续不可变，派生阅读副本的本地修改不自动传回远端。

## 必要接续验收

1. 在已有站点原型中明确“编辑原笔记”“阅读副本”“打开原文”和冲突/未知结果，再接桌面交互；沿用现有主题，不以本任务重设计工作区。
2. 使用一篇用户实际需要修改的原笔记，形成可见差异，通过既有受控动作提交，核对原文件、动作回执及 Hub 索引；不为验收给真实笔记添加测试句。
3. 两端真实变化、断网、重启/重复提交和目标移动没有现成样本时标明未验证，不制造来源内容或用单元样本冒充真实事件。
4. 各远端来源独立验收允许块/字段，再逐步扩大；当前没有完整任意富文本编辑或双向同步交付。

#26 保持打开。本次新增的是当前基础核对和真实只读验证入口，尚不满足修改/提交/远端回读等整体候选条件，也不将 #25 的只读浏览完成状态改写为编辑完成。
